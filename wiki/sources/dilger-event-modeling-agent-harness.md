# Martin Dilger — The Event Modeling Agent Harness (agents running 24/7)

Short LinkedIn post (with a diagram) by **[[martin-dilger]]**, captured 2026-06-17 via logged-in Chrome.
Source file: `raw/notes/dilger-event-modeling-agent-harness-24-7-loop.md`.

## What it says

Dilger describes — and has ChatGPT diagram — a concrete **"Event Modeling Agent Harness"**: agents
running **24/7 in a ralph-loop**, "looking for work," that he mostly doesn't pay for (local models).

- **The slice is the unit of work.** The harness's queue is made of [[event-modeling]] *slices*; an
  agent picks up the next slice marked **Ready** and works it through a state machine
  Draft → Ready → In Progress → Done. ("[[vertical-slice-architecture|Slice]] = unit of work.")
- **Anyone — human or agent — can model.** The harness doesn't care who authored or moved a slice;
  the next available agent acts on Ready slices. Continuous loop, "no bottlenecks / no delays."
- **The model is the backbone / feedback.** "Agents need feedback. The backbone of it all [is] Event
  Modeling — and especially the Given-When-Then scenarios provided by the model," leaning on BDD
  principles. (Cf. GWT-as-spec across the KB.)
- **Model split by task.** Local models (his most-used: Qwen3.6:9B on Ollama, in a ralph-loop) for
  coding; stronger models (mostly Sonnet) for modeling and for his **"WDYT" (what-do-you-think)**
  review skill; "rarely need Opus." Coding is "the easy part" once a **Blue-Print-Architecture** turns
  it into "painting by the numbers."
- **Coupling, not context window.** If coding needs strong reasoning or a "1-million-context" window,
  "you might revisit the reason for that — typically it's coupling."

## Why it matters here

This is the most explicit statement yet of Dilger's **[[event-modeled-agent-design]]** thesis as an
operating *harness*: it fuses the [[event-modeling]] slice (the unit of work + the spec via GWT) with
[[harness-engineering]] / [[agent-harness]] machinery ([[ralph-loop]], [[long-running-agents]],
[[unattended-coding-agents]]) and a Draft→Ready→Done control board. It sharpens his earlier
[[dilger-model-is-a-living-spec-always-on-agent|"living spec / always-on agent"]] post into a named,
diagrammed pattern, and it lands on the same conclusions as the substrate thread: keep work local and
loosely coupled so cheap models suffice ([[locality-of-reference]], [[context-engineering]],
[[vertical-slice-architecture]]). The "coupling, not context-window" line rhymes with
[[miller-codebase-is-the-prompt-vertical-slices-ai|Miller]], [[fritzsche-functional-core-imperative-shell-agentic-coding|Fritzsche]],
and (newly) [[vlad-khononov|Khononov's]] modularity argument.
