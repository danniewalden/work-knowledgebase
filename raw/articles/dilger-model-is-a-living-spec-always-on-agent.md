# The model isn't a diagram you draw once and forget

**Martin Dilger** — *LinkedIn feed post, 12h ago (captured via logged-in Chrome session)*

---

The model isn't a diagram you draw once and forget. It's a living spec - and when it changes, the code changes with it. Not the other way around.

We got this backwards for years. And I didn't fully understand how backwards until one morning this year - when I accidentally stumbled into the future.

We were running a workshop. Implementing a system in slices, like we always do. I had an agent running in the background in a loop - standard setup for us at this point.

The workshop ended. Everyone logged off.

I stayed behind to clean up the model. Made a few changes. Adjusted some slices. Nothing special - just the kind of tidying up you do after a long session.
That's what I typically do.

And then I noticed it.

The agent had never stopped. While I was quietly moving things around on the board, it was building. Picking up every change I made, in real time, without me ever saying a word to it.

I hadn't told it to. I had completely forgotten it was even there.

That was the moment. That was a smash-in-the-face.
Because up until that point, I thought of AI-assisted development as: model first, then hand it off, then wait. A sequence. A relay race with a clear baton pass.

What I was looking at was something completely different. There was no handover. No break. No moment where the human work stopped and the machine work began. It was just... one continuous flow.

I sat there for a minute and let it sink in.
What if you didn't need to touch a keyboard at all? What if you could speak your system into existence - someone models as you talk, and something else builds as you model?

That's not a productivity hack. That's a different way of thinking about what software development even is.

Today I have agents running 24/7, waiting for something to work on. The workflow looks like this - I place a Slice in "planned" and an agent will:
pick it up

- generate the tests from the spec - the harness
- implement it using the red tests as guidelines
- create a branch
- open a PR or merge, depending on the setup

No handover. No friction. No waiting.

And it can go even further - a modeling agent models, puts slices to "planned," and a builder agent takes over from there. Full autopilot. From spoken idea to running code, without a single person touching an IDE.

The spec isn't a stepping stone to the code anymore. The spec is the work. Everything else follows.

I was probably the one who learned the most in this workshop.
