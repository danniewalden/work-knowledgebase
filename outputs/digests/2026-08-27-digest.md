## Read next

### 1. Rico Fritzsche — "Why the Entity Model Is an Illusion: What Remains When You Model What Happens"
*ricofritzsche.me, 2026-08-26 · `raw/articles/fritzsche-why-the-entity-model-is-an-illusion.md` · **filed, not yet ingested***

**TLDR.** Fritzsche's sharpest statement yet of the entity-vs-event position: pre-defining entities makes systems rigid and forces you to anticipate things that aren't relevant yet. His worked example is vehicle rental — registration is *not* `CreateVehicle` ("that merely describes a database operation… the car rental company doesn't actually 'create' a vehicle") but the sequence `VehicleAcquired → VehicleReceived → VehicleInfleeted → VehicleReleasedForRental`. The "Vehicle" is then a **projection**, not an entity; a unique ID (artificial, or natural like a VIN) is only a *reference* against which you record what happened. Domain capabilities ("AcquireVehicle", "ReceiveVehicle") are autonomous and coherent, sharing only the event store and event definitions — "they know nothing about each other." The closing argument against load-mutate-save is quotable: it (1) destroys the information about what happened and (2) turns every concurrent request into a conflict, with audit/history/status/changelog tables read as workarounds for information the last-write row threw away.

**Why it's worth reading.** This is your top-priority thread — **business capabilities** — argued from first principles with a concrete domain, and it slots straight onto the [[autonomous-domain-capabilities]] / [[command-context-consistency]] line. The "perspective determines projection" point (purchasing vs. the repair shop) is also a clean justification for EM swimlanes you can reuse.

### 4. Martin Dilger — "Slice-based architecture is not really about slices" (the Element → Slice → Chapter → Story → Context ladder)
*LinkedIn, 2026-08-25 · `raw/notes/dilger-element-slice-chapter-story-context-ladder.md` · **filed, not yet ingested***

**TLDR.** A slice is only "the smallest building block you can model" — every slice either writes (command) or reads (read model). Group slices and you get a **chapter** (a consistent part of a business process or customer journey); connect chapters in order and you get a **story** (the whole flow); many stories together form a **context** (typically a complete system). His diagnosis: "most teams get stuck right there… they model slice after slice and never climb up to see the story, let alone the context."

**Why it's worth reading.** This is a genuine EM **method extension** with new vocabulary, and it does not yet exist anywhere in `wiki/concepts/`. If you model in slices, this is the missing zoom-out ladder — and it's the natural place to hang the business-capability/context boundary question.

### 5. Adam Tornhill — "Controlling the Uncertainty Machine: Do You Still Need to Read AI Code?"
*Code for Humans and Machines (Substack), 2026-08-20 · `raw/articles/tornhill-controlling-the-uncertainty-machine.md` · **filed, not yet ingested***

**TLDR.** "Human inspection is driven by uncertainty." Task uncertainty sets both how much autonomy you grant an agent and how deeply you review: a bug fix needs only the evidence (repro + passing test), the first iteration on a novel feature needs a spot-inspection of *structure*, never of all the code. The mechanism is **tests as the human/agent abstraction boundary** — have the agent write e2e tests first, then review and refactor *those* hard ("AI-generated application code is rarely optimal… but usually decent. The test code? Not so much"), then let the agent write whatever makes them pass. Two supporting moves: turn every review finding into a forward-looking skill rather than fixing it yourself, and **enforce deterministically whatever you don't inspect** (linters, CodeHealth MCP, custom architectural checks).

**Why it's worth reading.** For this wiki the punchline writes itself: **Tornhill's reviewed-e2e-test boundary is a slice's given/when/then.** It also completes a three-way triangulation with Willison's "More than just code review" (08-22) and Osmani's "Agentic Code Quality" — three independent authors concluding that reading every line is the wrong unit, all replacing it with a verification artefact.

### 6. Dan McAteer — "The Evolution of the Agent Harness"
*Latent.Space, 2026-08-22 · `raw/articles/mcateer-evolution-of-the-agent-harness.md` · **filed, not yet ingested***

**TLDR.** The best-argued *historical* account of harness engineering in the KB. Two curves — what the harness asks of the model vs. what the model can deliver — and the gap between them *is* agent effectiveness. Four dated stages: ReAct as "the harness on paper" (Oct 2022); AutoGPT/BabyAGI as "premature autonomy" (Spring 2023, with the compounding argument that 95% per-step reliability over 20 steps ≈ 36% success); Cursor/Copilot's "retreat to human in the loop" (2023–24, incl. Devin's ~15% Answer.AI result); and Claude Code as "the curves cross" (Feb 2025). Then Harness 2.0, the co-training era, with hard numbers — Harness-Bench: same model, same 106 tasks, **52.4 → 76.2 across harnesses**, a 23.8-point spread with zero model change. The loop is **train → absorb → shed → repeat**, ending in a harness for *human attention* rather than for the model.

**Why it's worth reading.** It gives you dated, numeric backing for "half the agent is the harness" — useful whenever you argue that the model isn't the variable worth optimising, and a good spine for the [[harness-engineering]] page.

*Also in the batch, lower priority but quick:* Dilger's **"Join considered harmful"** (`raw/notes/dilger-join-considered-harmful.md`) — read models are tailor-made per use case, so "there is simply no need to join in 99.9% of all use cases… we embrace redundant data… that's actually a precondition for sliced architectures" — the bluntest statement of that argument in the KB; and **MacManus/Pocock on the `/wayfinder` skill** (`raw/articles/macmanus-pocock-wayfinder-skill-fog-of-war.md`), on managing the "fog of war" of planning via a map/ticket/session vocabulary for orchestrating child planning sessions.
