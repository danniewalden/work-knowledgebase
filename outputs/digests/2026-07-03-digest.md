1. **"My Wife Asked Me to Build a Registration Form for a Flea Market" — Martin Dilger (LinkedIn, 2026-07-01)**
   `raw/notes/dilger-flea-market-model-code-deploy-30min.md` — *filed, not yet ingested*
   **TLDR:** A real story of using the Eventmodelers platform to brainstorm → model → build → deploy a working flea-market registration app (with an optional Stripe/Copecart payment path and a "who hasn't paid" filter button) in under 30 minutes, alongside a non-technical stakeholder (his wife, who "has no idea what Event Modeling is and doesn't care") — just by drawing the screens together.    **Why it's worth reading:** the most concrete "non-expert modeler + AI codegen" anecdote yet for your EM×agents thread, and it sharpens the "planning earns its keep as complexity grows" argument that ties `dilger-harness-is-20-percent-requirements-are-80` to `eventmodelers-ai`.

2. **"Extending Event Modeling: an optional 'Query' (WHEN) on the read side" — Martin Dilger (LinkedIn, 2026-06-29)**
   `raw/notes/dilger-extending-event-modeling-query-when.md` — *filed, not yet ingested*
   **TLDR:** Dilger's *first-ever* deviation from the Event Modeling "standard" — historically he refused to add elements ("stick to what Dymitruk defined"). Driven by repeated, independent feedback at the Munich EM Conference (and a prior discussion with Dymitruk), he adds an **optional `WHEN` named "Query"** to the read side of GWT: instead of `GIVEN event → THEN data available`, you can now write `GIVEN a user was registered / WHEN we query by email / THEN the user is returned` — a way to express complex read-side scenarios. Already live on the platform; feedback positive.
   **Why it's worth reading:** a rare change to the method's grammar itself, landing right on `given-when-then` — the acceptance-gate seam agents use — so it directly affects how a model specifies read-side behaviour to a coding agent.

3. **"Are you using Draw.io for Event Modeling?" (model-in-code, AI manipulation, MCP guardrails) — Martin Dilger (LinkedIn, 2026-06-30)**
   `raw/notes/dilger-drawio-event-modeling-model-in-code.md` — *filed, not yet ingested*
   **TLDR:** Agrees with the "we need the model in the code" instinct and concedes draw.io does a decent job (free, XML-serializable, lives in the repo) — but flags its drawbacks (non-technicians can't contribute; AI has *no framework/rules* so it errs; XML isn't human-readable; "what's not committed doesn't exist"). His alternative: export the model to a **standardized JSON**, version it in git, let a **local agent manipulate the JSON via provided skills**, and use the **MCP to validate changes pre-commit** — giving the agent guardrails/feedback so it self-corrects. Then visualize the JSON in the platform's Model-Viewer, and drive code-gen via Build-Kits (Node/Java/Kotlin).
   **Why it's worth reading:** the clearest statement of the "model-in-code + MCP-as-guardrail" agent-harness pattern from the eventmodelers.ai camp — feeds `event-modeled-agent-design`, `model-context-protocol`, and the EmLang/build-kits threads.

5. **"Event Sourcing: Aggregates, DCB, or what?" — Urs Enzler, planetgeek.ch (2026-06-23) — the one thing that *did* land in the wiki this window**
   [[enzler-event-sourcing-aggregates-dcb-or-what]] — *new wiki page*
   **TLDR:** A pragmatic "third way" in the aggregate-vs-DCB debate from a new-to-the-wiki practitioner. Enzler watched conference talks "making a big fuss" about aggregates and discussed DCBs with Sara Pellegrini — but his team never needed either. Instead they **design the concurrency away**: (a) "small data" + task-based UI (one command per task, only that task's data, no unit-of-work) so collisions are near-impossible; (b) replace concurrent designs with non-concurrent ones (student course-registration → draft-intent + a single-threaded batch that also enables prioritisation); (c) where serialisation is truly needed, use Azure Service Bus *sessions* to serialise within the boundary. Motto: "solve problems when they arise, not earlier." Caveat (his own): a low-concurrency HR/time-tracking domain, and no agents angle developed.
   **Why it's worth reading:** it completes the DCB debate on your substrate — DCB *removes* the boundary, conventional aggregates *shrink* it, Enzler *removes the concurrency* — a "you might not need it" counterweight to the Pellegrini/DCB and Fritzsche/CCC lines.
