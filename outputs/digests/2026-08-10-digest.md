## Read next

**1. Oskar Dudycz — "Fixing bugs in Event Sourcing is hard, for real?"** (Architecture Weekly / event-driven.io, 2026-07-27) — `raw/articles/dudycz-fixing-bugs-in-event-sourcing.md` — *filed, not yet ingested*
- **TLDR:** A worked hotel-pricing bug shows why fixing bad data is fundamentally easier under event sourcing than state. In a mutable model, a data-fix migration *overwrites the very evidence* you'd need to check it worked — so migration #2 is computed from migration #1's output, and one fix ends up repairing the last. Event-sourced, the original events are immutable, so every correction is computed from the booking, not the prior fix. Concrete primitives: put `metadata.buildSha` (the commit that appended the event) on events so you can query the exact rows a broken binary produced (900 real vs 340 merely-touched); fix-forward by appending a corrective event (`ReservationPriceCorrected`, the accountant's correcting-entry move) rather than editing the past; make correction a first-class command (`CorrectReservationPrice`, with permissions + a mandatory reason) so the bulk fix runs the same path a front-desk operator would — nobody `UPDATE`s prod at 23:00; and skip streams where a human already corrected the price so a blind recalc doesn't silently undo goodwill.
- **Why it's worth reading:** The strongest concrete "why events beat state" argument in the KB's substrate thread, and it hands you two reusable primitives (build-SHA event metadata; correction-as-a-command). Directly extends [[event-sourcing]] / [[event-versioning-and-upcasting]]; it's also the only thing waiting on your go/no-go to ingest.

**2. Martin Dilger — "The Shapes" (Event Modeling anti-patterns)** — `[[dilger-the-shapes-event-modeling-anti-patterns]]` / new concept `[[event-modeling-anti-patterns]]` — *new wiki page*
- **TLDR:** Names four EM anti-patterns recognizable by a board's *silhouette*: the **bed** (one screen driving many commands — the only hard red flag), the **left chair** (one command emitting many events), the **right chair** (one read model fed by many events), and the **shelf** (one slice absorbing all scenarios). Dilger's most-used AI-Skill, `/wdyt`, auto-detects them, challenges assumptions, and acts as a sparring partner.
- **Why it's worth reading:** Fills a gap the KB previously lacked (a named EM anti-pattern taxonomy) and lands the **agent-as-model-reviewer** seam — an AI grading the *shape* of a model upstream of the GWT code gate, squarely in your EM×agents focus.

**3. Adam Dymitruk — "AI melts the barrier / the model is the map"** — `[[dymitruk-ai-melts-barrier-event-modeling-is-the-map]]` — *new wiki page*

**5. Martin Dilger — "99% of software is boring: really just two patterns"** — `[[dilger-99-percent-software-boring-two-patterns]]` — *new wiki page*
