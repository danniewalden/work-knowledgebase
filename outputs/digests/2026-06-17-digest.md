## Read next

1. **Martin Dilger — "The Event Modeling Agent Harness" (agents running 24/7)** — *new wiki page, focus-tagged*
   `[[dilger-event-modeling-agent-harness]]` (raw: `raw/notes/dilger-event-modeling-agent-harness-24-7-loop.md`)
   **TLDR:** Dilger names and diagrams a concrete harness where the *queue is made of Event Modeling slices* moving through a Draft → Ready → In Progress → Done board, and any agent (or human) picks up the next Ready slice. The model's Given-When-Then scenarios are the BDD feedback backbone; cheap local models (Qwen3.6:9B on Ollama in a ralph-loop) do the coding while Sonnet handles modeling and a "WDYT" review skill. His punchline: if you think you need a 1M-token context or a frontier model to code a slice, the real problem is *coupling, not context window*.
   **Why it's worth reading:** This is the single most on-focus item this cycle — the clearest statement yet of your core EM×agents thesis expressed as an actual operating harness, fusing the EM slice with ralph-loop/long-running-agent machinery and a control board.

2. **Adam Tornhill — "CLEAR: Software Design Principles for the Agentic Age"** — *filed, not yet ingested (Substack note)*
   `raw/notes/tornhill-clear-design-principles.md`
   **TLDR:** Tornhill argues SOLID optimized for human maintainability, but agentic development introduces a new bottleneck he calls *reconstruction work* — the agent must infer structure from local context, so SOLID-compliant code can still be hard for an agent to reason about. His CLEAR set targets limiting a change's blast radius: **C**onceptual alignment, **L**ocal reasoning, **E**xplicit intent, **A**void search luck (consistent structures), **R**educe the edit surface. He frames it as re-emphasizing classics (Tell Don't Ask, Parnas's information hiding, DDD) that matter more under agents.
   **Why it's worth reading:** Directly extends the substrate/agent-legibility thread (Miller, Fritzsche) with a named principle set; a strong candidate to ingest as a concept page and cross-link to locality-of-reference and harness-engineering.

3. **Vlad Surganov (Atomic Object) — "CQRS and Event Sourcing in TypeScript: A Production Walkthrough"** — *filed, not yet ingested*
   `raw/articles/atomicobject-cqrs-event-sourcing-typescript-production-walkthrough.md`
   **TLDR:** A no-toy-code tour of CQRS + Event Sourcing + projections in a real NestJS / KurrentDB / PostgreSQL / Drizzle system. Covers commands-as-intent ("an executable glossary of your domain"), the aggregate as a TypeScript-enforced state machine, events as immutable facts, snapshots as disposable performance caches (the log is always authoritative), read-model vs. side-effect projections, event versioning via upcasters from day one, at-least-once idempotency, and PostgreSQL advisory-lock serialization per entity. Honest cost accounting closes it out.
   **Why it's worth reading:** Fills the missing concrete "how it actually looks in production" ES/CQRS source the KB has been wanting — grounds the substrate thread with implementation detail, and its "aggregate is a consistency boundary" framing ties straight into the DCB discussion.

4. **Borg, Hagatulah, Tornhill & Söderberg — "Code for Machines, Not Just Humans: Quantifying AI-Friendliness with Code Health Metrics"** — *filed, not yet ingested (arXiv 2601.02200, FORGE 2026)*
   `raw/papers/borg-tornhill-code-for-machines-not-just-humans.md`
   **TLDR:** Peer-reviewed study testing whether code quality predicts AI-friendliness, using LLM refactoring success on 5,000 Python files as the proxy. Finding: LLMs have significantly lower break rates on Healthy code (CodeHealth ≥9), a 15–30% risk reduction, and CodeHealth outperforms both perplexity and SLOC as a predictor of refactoring correctness. Conclusion: human-friendly code is AI-friendly code, so CodeHealth can flag where AI edits are low-risk vs. where human oversight is needed.
   **Why it's worth reading:** The independent, non-vendor empirical grounding for the code-health × harness thread — upgrades Tornhill's earlier LinkedIn reshare into a citable primary, and gives you a concrete metric for "agent-ready" code.

5. **Vlad Khononov — "The Golden Age of Modularity"** — *filed, not yet ingested (summary note)*
   `raw/notes/khononov-golden-age-of-modularity.md`
   **TLDR:** Khononov argues modularity is the property both modern architecture and AI/"vibe coding" depend on, with a two-part test: (1) it's clear which few components a change touches, and (2) the effect of a change is predictable. AI productivity only pays off when code is modular enough that changes stay local and effects stay predictable. Connects to his Balanced Coupling model (strength × distance × volatility).
   **Why it's worth reading:** A fourth independent voice converging on the same "keep it local and loosely coupled so cheap models suffice" conclusion as Dilger, Miller, and Fritzsche — useful as the coupling/modularity anchor for the substrate thread.
