## Read next

**1. Oskar Dudycz — "Fixing bugs in Event Sourcing is hard, for real?"** (Architecture Weekly / event-driven.io, 2026-07-27)
`raw/articles/dudycz-fixing-bugs-in-event-sourcing.md` — **filed, not yet ingested** (the one fresh unprocessed input).
*TLDR:* Uses a hotel tourist-tax bug to show why fixing bad data is *harder* in a state model than in event sourcing. In the mutable model a fix-migration overwrites the very evidence (booking date, original total, which rows the broken build produced) you'd need to verify it — so migration two is written against migration one's output, and attempt three repairs attempt two. Event-sourced, the original events are immutable, so every correction is computed from the booking, not the prior fix. Four concrete primitives: (1) an event `metadata.buildSha` to query the exact rows a broken commit wrote (900 real vs 340 merely-touched) plus correlation/causation IDs; (2) fix-forward by appending a corrective event (`ReservationPriceCorrected` — the accountant's correcting entry), never editing in place; (3) make correction a first-class command (`CorrectReservationPrice`, with permissions + mandatory reason) so the bulk fix runs the same path as a front-desk operator — "nobody UPDATEs prod at 23:00"; (4) skip streams where a human already posted a price-affecting correction, so a blind recalc doesn't silently undo a goodwill discount.
*Why it's worth reading:* The sharpest practical case yet in the KB for *why* an append-only log pays off operationally, and it hands you a reusable pattern (buildSha metadata + corrective-command) that sits right on the [[event-sourcing]]/[[event-versioning-and-upcasting]] substrate and the "make correction a requirement" seam. Also a clean [[agent-explainability]] echo: the correction event records *why*, for the next reader.

**2. Event Modeling Anti-Patterns ("The Shapes")** — new concept page
[[event-modeling-anti-patterns]] — **new wiki page** (focus-tagged).
*TLDR:* Dilger's diagnostic vocabulary for reading an event model by its **silhouette**: *the bed* (one screen, many commands — the only hard red flag), *the left chair* (one command, many events), *the right chair* (one read model, many events), *the shelf* (one slice, all scenarios). Severity is graded — only the bed is categorical; the rest are "look closer" heuristics. Built to be **agent-operable**: his `/wdyt` skill walks a model and calls the shapes out, and a mooted "linter" grades a board's structure against a curated reference catalog.
*Why it's worth reading:* This is the crisp statement of the newest addition to your focus area — the agent as *model reviewer*, a quality gate upstream of the [[given-when-then]] code gate. Two pages, five minutes, and it reframes how [[event-modeled-agent-design]] now works.

**3. Dilger — "Agentic collaboration on freeform drawings"** (LinkedIn, ~08-09)
[[dilger-agentic-collaboration-freeform-drawings]] — **new source page**.
*TLDR:* eventmodelers.ai now lets you sketch freeform on the board alongside the structured "Chapters" grid; the agent *reads* the drawings for spatial/graph context (what's inside a lasso, where an arrow points) and, via MCP, *draws back* — sketches, arrows, question marks — so `/wdyt` returns visual annotations, "like a remote colleague joining the board."
