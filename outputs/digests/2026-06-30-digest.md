**1. Dilger — "The harness is 20%, the requirements are 80%"** *(new wiki page — `[[dilger-harness-is-20-percent-requirements-are-80]]`; tight EM×agents focus)*
TLDR: Dilger's sharpest framing yet of his recurring thesis. Everyone is building elaborate AI harnesses — agents, roles, skills, guardrails — but the harness and the code are only ~20% of the solution. The other 80% is clarifying requirements and understanding business processes well enough to express them in a format the agent can use ("nobody tells you how to write that damn markdown"). That 80% is a human/communications problem with *no technical fix*; clear it (via Event Modeling) and the rest "becomes pretty easy."
Why worth reading: It's a pointed challenge to the whole harness/loop-engineering thread you've been building — it argues the leverage is upstream in the spec, not in the scaffolding, and ties [[harness-engineering]] ↔ [[event-modeled-agent-design]] ↔ [[spec-driven-development]] in one line you'll want to quote.

**2. Fritzsche — "Clean Architecture is untouchable / capability over layers"** *(new wiki page — `[[fritzsche-clean-architecture-capability-over-layers]]`; business-capabilities, flagged important)*
TLDR: A direct swing at the Clean Architecture diagram. Dependency Inversion only flips the *direction* of dependencies — it doesn't remove the functional dependencies inside the behavior; business logic still depends on I/O. Real Separation of Concerns isn't horizontal technical layers, it's the **domain capability**. CRUD is not domain language (experts think in processes, decisions, state transitions), and Functional Core / Imperative Shell is the stronger foundation for coherent capabilities. Credits Ralf Westphal's work on functional dependencies.
Why worth reading: Goes straight at your flagged-important [[business-capabilities]] thread, sharpening the "capability, not layer, is the boundary" argument that underpins agent-ownership boundaries.

**3. Fritzsche — "An atomic append isn't enough: CCC needs a serialized write order"** *(new wiki page — `[[fritzsche-ccc-atomic-append-serialized-write-order]]`; substrate / DCB-CCC)*
TLDR: The implementation layer beneath Command Context Consistency. A PostgreSQL CTE that bundles the Event-Query check with the insert makes each append *atomic*, but under READ COMMITTED two concurrent commands can observe the same context version, reach identical decisions, and *both* append. To get CCC you also need a protected **write order** — e.g. lock one metadata row per append transaction, serializing physical writes globally while the conflict decision stays local to the command context. "Atomicity safeguards one append; serialization prevents two decisions from the same observed context being accepted."
Why worth reading: The concrete contract under [[dynamic-consistency-boundaries]] / [[autonomous-domain-capabilities]] — if you ever reason about whether an event-sourced capability is a safe agent-ownership unit, this is the correctness detail that has to hold.

**4. Tornhill — "You cannot trust your coding agent to produce maintainable code" (CodeScene MCP)** *(new wiki page — `[[tornhill-cannot-trust-agent-codescene-mcp]]`; agentic-coding / harness)*
TLDR: Told to fix a code-health issue in already-poor code, his agent traded one problem for a worse one. Three reasons "follow SOLID"/"write clean code"/LLM-reviews-LLM don't work: LLMs are non-deterministic, they can't reliably self-assess code health, and the messy existing code *is* the context — so agents do worst exactly where they're needed most. Fix: a **deterministic external sensor** (CodeScene MCP) as the agent's source of truth instead of self-judgment. He's coded 100% agentically for 9 months.
Why worth reading: The sharpest practitioner version of the code-health-as-harness-sensor pattern and the behavioral punchline under the peer-reviewed [[borg-tornhill-code-for-machines-not-just-humans]] study; a clean computational-sensor-beats-inferential instance for [[harness-engineering]].

**5. Kulkarni/Thoughtworks — "Building Reliable Agentic AI Systems" (Bayer PRINCE)** *(new wiki page — `[[martinfowler-prince-building-reliable-agentic-ai-systems]]`; harness + context-engineering, production)*
TLDR: A rare *independent, regulated-enterprise* production case. Bayer's PRINCE assistant over decades of preclinical reports — agentic RAG + Text-to-SQL on LangGraph, with a Clarify→Think&Plan→Researcher→Reflection→Writer flow, **three reflection loops** (process/data/draft), LLM fallbacks + node-level state-persistence recovery (resume from the failed node), per-sentence citation explainability, and Langfuse/RAGAS evals. Core lesson: bigger context windows didn't remove the need to route the *right* context to the *right* agent.
Why worth reading: The strongest outside corroboration that your harness + context-engineering vocabulary describes how reliable agentic systems are actually built — a real system that arrived at the framing on its own, with concrete patterns for [[multi-agent-orchestration]], [[agent-explainability]], and [[agent-observability-and-evals]].
