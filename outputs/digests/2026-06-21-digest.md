## Read next

1. **Rico Fritzsche — "Event Sourcing does not require aggregates (CCC vs DCB)"** — `[[rico-fritzsche-es-does-not-require-aggregates-ccc-vs-dcb]]` · *new wiki page (ingested 06-21)*
   - **TLDR:** Two tight claims. (1) **Event sourcing does not require aggregates** — ES is defined by the persisted event history as source of truth, with appends decided from that history; the DDD "rebuild aggregate from stream, append at expected version" is *one implementation, not the definition.* (2) **CCC and DCB are the same principle at different layers, and neither is a synonym for ES**: both reject an append if the command's relevant event context changed first, but **CCC** is the representation-agnostic *principle* while **DCB** is a specific tag-based *event-store contract* (tags = the write-time query contract, payload opaque). CCC is the conceptual guarantee; DCB is one store contract that applies it.
   - **Why it's worth reading:** Directly on your flagged **business-capabilities / autonomous-domain-capabilities** thread and the DCB substrate — and it closes a question the KB had left open on both `[[dynamic-consistency-boundaries]]` and `[[autonomous-domain-capabilities]]`. (Caveat: Fritzsche's own framing; DCB proponents may not accept "CCC is the more general principle.")

2. **Martin Dilger — "Build kits: model to generated code in 30 seconds"** — `[[dilger-build-kits-model-to-generated-code]]` · *new wiki page (ingested 06-21)*
   - **TLDR:** Pitches "build kits" for eventmodelers.ai — model a slice, hand it to an agent, get a best-practice reference implementation in seconds. The framing is pedagogical: Dilger learned event sourcing with "literally zero real-world examples," and build kits collapse that; an anecdote has someone with *zero* ES experience model two slices and let an agent build them, claiming ~10x faster learning by watching the model become code and iterating. Explicit caveat from him: not "deploy to production immediately."
   - **Why it's worth reading:** A concrete, fresh instance of the tight EM×agents loop — the EM slice as the unit handed to a coding agent — now reframed as a *learning on-ramp*. Short, on-focus. (Vendor self-report; "30s/10x" are promotional.)

3. **Martin Dilger — "Event Modeling as a knowledge hub; EmLang support"** — `[[dilger-event-modeling-knowledge-hub-emlang]]` · *new wiki page (ingested 06-21)*
   - **TLDR:** Reframes Event Modeling as a **knowledge hub**, not "modeled software": the problem isn't ignorance but *scatter* (knowledge fragmented across tickets, Confluence, code, Slack, heads), and EM is the single accessible place to understand how a system works — which then doubles as the blueprint humans and agents build from. Format-agnostic and access-first: author on the platform, or import YAML/JSON/Markdown, or have an agent add knowledge via **MCP**. Concrete change: added **EmLang** (a YAML dialect) as an import format.
   - **Why it's worth reading:** Generalizes Dilger's "model is the source of truth" into a queryable system-of-record for both humans and agents — and the MCP-ingestion / format-pluralism move echoes the prooph board / Fraktalio "agents author the model via MCP" pattern. (Note the resonance with this KB's own premise. Vendor vision; "EmLang" cited without a captured spec.)

4. **Golo Roden — "Event Sourcing meets MCP: The whole story for LLMs"** (the native web / heise, 2026-04-02) — `raw/notes/roden-event-sourcing-meets-mcp-whole-story-for-llms.md` · *filed, not yet ingested*
   - **TLDR:** Pairs two standards: **event sourcing** supplies complete business-language history (CRUD is "only the last chapter of the book"; events are the whole book), and **MCP** is the data-agnostic bridge that makes it reachable by any LLM in natural language. *"An average model with excellent context beats a top model lacking context."* Worked library-domain example shows an LLM answering questions impossible against a CRUD snapshot, with no pre-built read model; argues events are the natural language for LLMs and ties it to context engineering.
   - **Why it's worth reading:** The cleanest **event-sourcing × MCP × context-engineering** statement — pairs naturally with today's Dilger "EM as MCP-fed knowledge hub" item and would add a new ES-vendor voice (EventSourcingDB). Highest-value pending compile.

5. **AxonIQ (Reeves & Buijze) — "AI Agent Explainability: Why Your Infrastructure Needs to Remember"** (AxonIQ blog, 2026-04-23) — `raw/articles/axoniq-ai-agent-explainability-why-infrastructure-needs-to-remember.md` · *filed, not yet ingested*
   - **TLDR:** Agent explainability is an **architecture/infrastructure** problem, not a model problem. State-based systems overwrite the causal history regulators now demand (EU AI Act, SR 11-7, GDPR Art. 22); event sourcing makes every agent decision a permanent, replayable, queryable record. Sharp **event store vs. event stream** line (Axon captures *why*; Kafka only moves *what*), plus a claim that the Axon command/event/projection model resists AI hallucinations in code generation.
   - **Why it's worth reading:** Corroborates Roden from the audit/compliance angle and supplies the regulatory framing the ES-as-agent-memory thread was missing.

6. **Borg, Hagatulah, Tornhill & Söderberg — "Code for Machines, Not Just Humans"** (arXiv 2601.02200; accepted FORGE 2026) — `raw/papers/borg-tornhill-code-for-machines-not-just-humans.md` · *filed, not yet ingested*
   - **TLDR:** The **peer-reviewed primary** behind Tornhill's "unhealthy code costs more in the agentic era" claim. On 5,000 Python files, AI-refactoring success is the proxy for AI-friendliness: LLMs break **Healthy** code (CH ≥ 9) far less often (**15–30% risk reduction**), and CodeHealth **beats perplexity and SLOC** as a predictor. Conclusion: human-friendly code is also machine-friendly; quality is a prerequisite for safe AI adoption.
   - **Why it's worth reading:** Rare *independent, academic* grounding for the code-health × agentic-coding thread — ingesting it upgrades that line from a vendor reshare to a citable result.
