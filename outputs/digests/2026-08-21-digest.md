## Read next

**1. Oskar Dudycz — "Vertical slices, their ownership and external dependencies"** (Event-Driven.io, 2026-08-10)
`raw/articles/dudycz-vertical-slices-ownership-and-external-dependencies.md` — *filed 08-15, **11 days** un-ingested*

**TLDR.** Dudycz answers the question the vertical-slice literature keeps dodging: what does a slice do when it needs something it doesn't own? First he untangles the vocabulary — a **slice** is one piece of functionality cut through all layers ("more a function than an entity"); a **module** is a logical grouping of slices, grouped by *what changes together*; a **bounded context** is "a **linguistic barrier**," a set of functionality the business uses one vocabulary for. His sharpest correction: a frontend and a backend are not two contexts, they're two deployment targets, and "seven features of one application are almost always slices, or at most modules, sitting inside a single context — that's good news, because it means they were never obliged to be autonomous." Then the positive rule set: *everything outside the slice is external, whether it's the next folder or another system*; declare **narrow function types where they're used, in your own vocabulary**, rather than importing a wide interface; compose by passing functions in at the composition root; reuse policies and calculators and **let handlers duplicate**; business logic per entity, read model per query, schema per module. And the closer that matters most here: **"this approach helps LLM agents too"** — everything a feature needs sits in one folder with a handful of function types crossing the boundary, so "the same property determines how much can fit in a context window and how much of a codebase an agent has to read before it can safely change one behaviour. A layered structure that needs five folders touched for one feature costs an agent the same way it costs us, faster."

**Why it's worth reading.** This is the strongest un-ingested item on your **top-flagged** priority: it gives `[[business-capabilities]]` a rigorous slice/module/context distinction from a primary, and it independently derives the *comprehension-debt* argument for agents from the substrate side rather than the harness side.

**2. Andrew Miracle — "My Loop Engineering Workflow"** (andrewmiracle.com, 2026-08-10)
`raw/articles/miracle-my-loop-engineering-workflow.md` — *filed today, not yet ingested*

**TLDR.** "I don't have a prompt. I have a triangle of loops… The prompt is maybe five percent of the outcome. The loops are the rest." Three nested loops — **session** (hours: opens on a written commission, closes on a structured closeout/handoff), **sprint** (days: research→plan→execute→retro), **program** (weeks: PROJECT.md + phased ROADMAP.md → packets) — and it's a *triangle rather than a stack* because every scale runs the same grammar (**objective → execution → feedback → refined objective → …**) with the same start and end point. "That refinement step is why the loop converges instead of spinning." Four things in it are new to the KB. (a) **Execution is fork-join** — Doug Lea / Cilk lineage, with four deliberate deviations: the fork is an *approved dispatch plan*, not a thread pool; workers are *durable branch-keyed children in isolated git worktrees*, not anonymous stealers, so "the shared-state hazard fork-join frameworks spend so much effort containing never materializes, because ownership is assigned at the fork instead of negotiated during execution"; **"the join is a gate, not a barrier… It doesn't merge output. It merges confidence"**; and by Amdahl, "generation parallelized; verification did not" — so the serial work *moved to the join rather than shrinking*. (b) **Three sequenced non-advisory gates**: a plan-checker whose context is never shared with the planner ("rather than the planner grading its own homework"), a *Nyquist test gate* (sample the change surface densely enough to reconstruct what was actually built and catch where it aliases from what was asked), and a **goal-backward verifier** — "for every requirement in the plan, where in the diff is it satisfied? Any requirement without evidence fails the audit, even if all the tests pass." (c) A **trust ledger** hook on every tool call: sessions start at 50/100 (L2), levels gate capability (L1 edit → L2 mutating bash/spawn → L3 push/PR/deploy → L4 destructive), Fibonacci-scaled deductions (delivery miss −5, unverified claim −8, fabrication −13, tampering with the ledger −21, self-report a flat −3 "because disclosure should always be cheaper than discovery"), terminated below 20. "It works because it prices honesty into the system." (d) **Documents over conversations** at every handoff — "documents survive context windows; conversations don't" — autoCompact deliberately off, and *restatement as the only compaction-proof memory*.

**Why it's worth reading.** Three separate seams land at once: the **goal-backward verifier is exactly what a GWT-per-slice event model supplies as a rubric**, which strengthens `[[event-modeling]]`↔`[[loop-engineering]]` from the loop side; the Amdahl/join argument is a *mechanism* for `[[orchestration-tax]]`/`[[parallel-agent-limit]]` rather than another anecdote; and his "give your harness explicit context layers" prescription is a near-exact independent rediscovery of the `[[karpathy-llm-wiki]]` pattern this KB itself runs on.

**3. Nick Tune — "Enforced application architecture for agents and humans"** (nick-tune.me, 2026-08-13)
`raw/articles/nick-tune-enforced-application-architecture-agents-humans.md` — *filed 08-17, not yet ingested*

**TLDR.** The complaint is concrete: agents don't follow architectural guidelines written in skill files, ADRs, or markdown anywhere in the repo — so **enforce the architecture in the build instead**. His iterated approach: classify packages by *type* (`domain-model` vs CLI app) rather than writing one global ruleset; prefer broad layer-level import rules over fine-grained role-based ones; and above all **enforce domain isolation** — "if you're only going to add one convention, that's probably the best one." Demonstrated as a working TypeScript/NX DSL where a `packages/{subdomain}/domain-model` package may contain only code annotated `aggregate | value-object | domain-event | domain-port | domain-service | domain-error`, anything else is a hard build failure, and the only permitted cross-subdomain import is a versioned published language.

**Why it's worth reading.** It's the deterministic enforcement layer missing under the whole capability/slice-ownership line — the compiler-level counterpart to Dudycz's convention (#1) and to Miracle's gates (#2). Reads as the third leg of the same ingest.

**4. Martin Dilger — "Loop Engineering – Or Why You Should Never Argue With an Agent"** (eventmodelers.ai, 2026-06-10)
`raw/articles/dilger-loop-engineering-never-argue-with-agent.md` — *flagged for accept/reject on 08-18, **still pending 3 days***

**TLDR.** Loop engineering as *deliberate simplicity*: a task list, one task per iteration, record the learnings, then **wipe the context completely** and start the next task clean. His mechanism claim is stronger than anything else in the KB — hallucination isn't stochastic, it's *structural*: "confusion is what produces hallucination… the predictable result of a polluted context window," and the standard reaction (prompt harder, add rules in capitals) makes it worse, because an agent will always agree with your correction while carrying the confusion forward. So: rule broken → no discussion → discard everything except the learnings → retry. The load-bearing line for this wiki is *"Event Modeling Is 'Loop Engineering' Applied"* — the hard part of a loop is defining the task list, and in Event Modeling every slice already **is** a task. He also plants an anti-maximalist flag: the moment you add state, memory and decision-making between iterations, you reintroduce what the loop was designed to remove.

**Why it's worth reading.** Now more valuable than it was yesterday, because Miracle (#2) is its exact foil: Miracle *engineers* the durable state between iterations that Dilger says destroys the loop. Ingesting the two together gives `[[loop-engineering]]` a real recorded disagreement instead of a consensus summary — and Dilger is the only voice stating the loop↔slice↔EM seam from a primary rather than the KB inferring it.

`raw/articles/laycock-the-conductor-developer.md`, `laycock-citizens-build-agents-execute-experts-govern.md`, `willison-conceptual-integrity-and-counting-lines-of-code.md` — *filed 08-20, ingest approved-but-not-run*

**TLDR.** Three pieces that say one thing from three vantage points. **Laycock (Conductor)**: she expected the bottleneck to migrate coding → design → architecture → verification and says flatly *"I was wrong"* — it's **human attention**; the best developers aren't in flow, they're conducting, because "someone has to hold the whole system in their head," and practitioners cap out at *"Ten. Twelve. Beyond that, they become the bottleneck."* **Laycock (Citizens/Experts)**: the scarce resource is **engineering judgement**; experts become "dramatically more leveraged," designing guardrails, platforms and feedback loops — and "when agents can generate lots of code very quickly, good design matters **more**, not less." **Willison**: lines of code *are* a real signal because there was a human ceiling (50–60 debugged lines a day, 200 = "an incredibly good day"), but the new limit is cognitive — "I can churn out code a hundred times faster. I don't have the cognitive capacity to stay on top of 100 times the amount of code" — and what agents erode is Brooks' **conceptual integrity**: discipline used to be enforced by the *cost of time*, and at one hour per feature that filter is gone.

**Why it's worth reading.** Miracle's Amdahl-at-the-join argument (#2) supplies the *formal* version of what these three describe informally, so the cluster is now a four-source convergence on "what the human is for" — CTO, IC, and harness-builder independently.
