### 1. Making Your Data Ready for Agentic AI — Pramod Sadalage & Prem Chandrasekaran (martinfowler.com, 2026-08-27)
`raw/articles/sadalage-chandrasekaran-making-data-ready-for-agentic-ai.md` — **filed, not yet ingested (Batch B)** · 9,941 words

**TLDR.** Thirty years of data architecture assumed a human consumer who supplies the missing context and hesitates when a number looks wrong; an agent supplies neither and acts confidently on whatever it's handed. The authors propose three layers — a trusted data foundation, a **context layer** (semantic model + domain model + **capability model**), and a governed access layer — plus continuous lineage. The capability model is the load-bearing part: a curated set of operations where each one declares permissions, an owner, **preconditions checked deterministically against live state at the moment of acting**, and a **reversibility class**. Two claims sharpen it: *"reversibility predicts safe autonomy better than the size of the transaction"* (a $50k reversible ledger correction is safer to automate than a $200 irreversible external payment), and *"retrieved text informs, it never gates"* — rules are extracted from prose documents ahead of time, curated by a human, and stored as declared preconditions, so a poisoned document cannot grant a permission the agent didn't already have.

**Why it's worth reading.** This is the only outstanding item in your flagged-important **business capabilities** thread — the rest of that corpus (Devadoss CEAD, Fritzsche, Skelton, Homann) is already compiled — and it adds a genuinely new axis to `autonomy-ladder` rather than restating the page. The reversibility framing is the kind of thing you'd want in a slice's precondition vocabulary.

### 2. The self-training Event Modeling agent — Martin Dilger (LinkedIn, 2026-08-27 & 08-28)
`raw/notes/dilger-one-million-tokens-self-training-modeling-agent.md` + `raw/notes/dilger-modeling-agent-improved-by-learning-loop.md` — **filed, not yet ingested (Batch A)** · ~780 words for the pair

**TLDR.** Dilger built a grading loop for the Eventmodelers modeling agent: give it a realistic requirement set, have it model it, then **structurally diff** the result against a corpus of hand-crafted "good" event models (are Chapters laid out the same way? are Read Models structured similarly? how are given/when/thens shaped?), let it rewrite its own skills from the differences, and re-model — comparing each round to both the previous version and the good corpus. Running locally on QWEN3.7:27b, it independently discovered three of his unwritten conventions: storylines instead of plain GWT for Read Models attached to Automations, linked elements to bridge events across chapters, and Read-Model/Screen copies instead of back arrows. The follow-up post adds the failure mode: **roughly every fifth iteration is bad** — the model takes shortcuts as it nears its token budget, "trained to make the best with the budget they have."

**Why it's worth reading.** This is the KB's first worked instance of Event Modeling used as a **verification rubric for a self-improving agent** — the exact claim `event-modeled-agent-design` has been asserting without evidence — and it's the cheapest batch in the queue by far. The budget-threshold cliff is an unattended-loop failure mode nothing in the wiki currently covers.

### 3. Model-as-Code vs Model-as-Language — new concept page
`[[model-as-code-vs-model-as-language]]` — **new wiki page, written 2026-08-30, tagged `focus`**

**TLDR.** Written up as an explicitly *unresolved* controversy. Dilger: "The Markdown we use is a suggestion dressed up as a spec… Event Modeling is the one [language] that works for me" — model authored first, code generated from slices. Miller: "not enthusiastic about any of the intermediate DSL approaches… using YAML, XML, or custom built textual DSLs… better off just adding the visualization capabilities on top of the code" — code first, model recovered by visualization. The page's best work is the *agreements*: both reject prose-as-spec, both treat the slice as the unit, both read VSA as token economics rather than taste, both are pushing EM concepts into the runtime.

**Why it's worth reading.** It's a direct test of your `.chspec.yml` premise — Miller names and rejects precisely the "intermediate textual DSL" that approach rests on, and the page argues honestly that the answer has to be empirical because nobody has run the comparison. It also identifies a missing rung in `agent-readable-model-artifacts`: *derived* model artifacts, where the export is a projection of code.

### 5. Vertical slices, their ownership and external dependencies — Oskar Dudycz (event-driven.io, 2026-08-10)
`raw/articles/dudycz-vertical-slices-ownership-and-external-dependencies.md` — **filed, not yet ingested (Batch I)** · 3,828 words · **21 days waiting, the oldest on-focus item**

**TLDR.** Dudycz takes five recurring VSA questions — does a slice get its own table? are seven areas seven bounded contexts or seven slices? how does a "verify order" slice read what "register order" wrote? where does cross-module fetching code live? — and collapses them into one: *what does a slice do when it needs something from the outside world?* His diagnosis is that calling every application area a bounded context sets the separation bar as high as it goes, after which every connection looks like a violation and none of the questions has a legal answer.

**Why it's worth reading.** This is the explicit **VSA ↔ slice ownership** mapping the watch config has been asking for since June, and it's the piece of the substrate thread most directly applicable to how you'd carve a real model. It's also the longest-waiting on-focus capture in the queue.
