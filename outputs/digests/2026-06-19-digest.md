## Read next

1. **Rico Fritzsche — "RPU/Reactor vocabulary" (Request Processing Units and Reactors / The domain is defined by capabilities, not object models)** — `[[rico-fritzsche-rpu-reactor-vocabulary]]` · *new wiki page (ingested 06-19)*
   - **TLDR:** Fritzsche retires his own "Feature Slice" term for a precise vocabulary: an **RPU** is an atomic, self-contained processor for one Command/Query capability (now decoupled from transport — HTTP pushed out into a thin Delivery Mechanism); a **Reactor** is an optional lightweight coordinator of several RPUs for one user **Interaction** (explicitly *not* a saga, event handler, or projection); **Use Case**, **Providers** (injected infra), and **Event Store** (= application state) round it out. The deeper companion argues layered architecture is "distributed technical ownership" — one capability smeared across controller/service/repo/entity/mapper — and that the **domain capability**, not an object model or DDD aggregate, must be the ownership boundary, behaving as a deterministic functional core over immutable facts.
   - **Why it's worth reading:** This is the most worked-out statement yet of your flagged-important **business-capabilities** thread — capability-as-the-agent-ownership-boundary — and it sharpens the VSA/locality substrate at the same time. (Caveat: still one author's coinage, no independent adoption.)

2. **Golo Roden — "Event Sourcing meets MCP: The whole story for LLMs"** (the native web / heise, Apr 2026) — `raw/notes/roden-event-sourcing-meets-mcp-whole-story-for-llms.md` · *filed, not yet ingested*
   - **TLDR:** Pairs two standards to solve two problems: **event sourcing** supplies complete, business-language history (CRUD is "only the last chapter of the book"; events are the whole book), and **MCP** is the data-agnostic bridge that makes that history reachable by any LLM in natural language. Key line: "An average model with excellent context beats a top model lacking context" — and an event store, unlike a CRUD-over-MCP snapshot, gives the model "the whole story." Worked library-domain example + the free EventSourcingDB MCP Server (Mar 2026); argues events are *the natural language for LLMs* (business-named, chronological narrative, self-contained context).
   - **Why it's worth reading:** The cleanest articulation of the **event-sourcing × MCP × context-engineering** bridge — directly extends your EM×agents focus and pairs with the AxonIQ piece below. A new vendor voice (EventSourcingDB) distinct from Axon/Critter Stack.

3. **AxonIQ (Reeves & Buijze) — "AI Agent Explainability: Why Your Infrastructure Needs to Remember"** (AxonIQ blog, Apr 2026) — `raw/articles/axoniq-ai-agent-explainability-why-infrastructure-needs-to-remember.md` · *filed, not yet ingested*
   - **TLDR:** Argues agent explainability is an *infrastructure*, not a model, problem: state-based architectures overwrite the causal history regulators now require (EU AI Act, SR 11-7, GDPR Art. 22), while event sourcing makes every agent decision a permanent, replayable, queryable record. Draws a sharp **event store vs. event stream** line (Axon Server captures *why*; Kafka only moves *what*), and notes the Axon programming model is "unusually resistant to AI hallucinations" in code generation because its commands/events/projections structure gives generators a precise pattern to follow. Promotional, but the architecture argument is the substance.
   - **Why it's worth reading:** Corroborates Roden from the audit/compliance angle and supplies the regulatory framing your ES-as-agent-memory thread was missing; the "structured ES resists hallucinations" claim ties back to harness/agent-legibility.

4. **Martin Dilger — "Done is Done" (OCP = a new slice, not an extension)** — `[[dilger-done-is-done-open-closed-new-slice]]` · *new wiki page (ingested 06-19)*
   - **TLDR:** Reframes the Open-Closed Principle as a slice decision: build new behavior without touching working code — a Guest-Invitation is a *new slice*, not an edit to an existing one. Dilger modeled it in 30 minutes so an agent could implement it while he taught a workshop; argues this design-time move avoids migrations/upcasters on a live event-sourced system and favors coupling-awareness over reuse.
   - **Why it's worth reading:** A crisp, concrete instance of the tight EM×agents loop — model-a-slice-then-let-the-agent-build-it — and the cleanest practical link from OCP → VSA slice-as-unit-of-addition.

5. **Oskar Dudycz — "Announcing Strictland — contract testing for message compatibility"** (Event-Driven.io, 2026-06-15) — `raw/articles/dudycz-strictland-contract-testing-message-compatibility.md` · *filed, not yet ingested*
   - **TLDR:** A new JVM OSS library for **event/message schema compatibility**: serialize a message in an ordinary unit test, snapshot the JSON into the repo, and fail the build when the shape drifts (`thenContractIsUnchanged`) or when versions stop reading each other (`thenBackwardCompatible` / `thenForwardCompatible`). Deliberately smaller than Pact/Schema Registry — no broker, no Docker, contract is a diffable file in your repo; .NET and TS ports planned.
   - **Why it's worth reading:** A practical, repo-local take on the `[[event-versioning-and-upcasting]]` problem — the same "avoid upcaster pain" tension Dilger raises in item 4, but solved as a fast test gate. On-thread for the substrate.

6. **Oskar Dudycz — "You can fork a package, but can you own it?"** (Event-Driven.io, 2026-06-08) — `raw/articles/dudycz-fork-a-package-can-you-own-it.md` · *filed, not yet ingested (mostly off-thread)*
   - **TLDR:** Riffs on Hashimoto's "fork your dependencies" advice to argue the real issue is *deciding* to own a dependency, not forking it: inventory (SBOM), criticality, bus factor, and a concrete mitigation plan. The on-thread hook is the **"LLM as a fork"** section — LLMs lower the cost of *producing* code, not *owning* it; "vibe it and move on" is the same missing decision as "install and move on," a fresh flavor of Shadow IT.
   - **Why it's worth reading:** Short and largely tangential, but the LLM-ownership argument is a useful counter-weight to agentic-coding optimism — read the last two sections only if pressed for time.
