**3. Extending Event Modeling: an optional "Query" WHEN on the read side — Martin Dilger, LinkedIn, 2026-06-29**
`raw/notes/dilger-extending-event-modeling-query-when.md` — *filed, not yet ingested*
TLDR: Dilger's **first-ever deviation from the Event Modeling "standard"** — after discussions at the Munich conference (and prior conversations with Dymitruk), he adds an optional `WHEN` named "Query" to the read side of GWT: `GIVEN a user was registered / WHEN we query with the user's email / THEN we expect the user returned`, letting scenarios express complex queries rather than leaving `WHEN` out. Already shipping on the platform with positive feedback.
Why it's worth reading: A rare change to the EM notation itself, from the practitioner closest to the standard; directly touches [[given-when-then]] — the agent acceptance-gate seam in your EM×agents thread.

**4. Are you using Draw.io for Event Modeling? (model-in-code, MCP guardrails) — Martin Dilger, LinkedIn, 2026-06-30**
`raw/notes/dilger-drawio-event-modeling-model-in-code.md` — *filed, not yet ingested*
TLDR: On keeping "the model in the code." Acknowledges clients export draw.io XML and let AI manipulate it directly, but lists the drawbacks (non-technicians can't contribute, AI has no rules/framework so it errs, XML isn't human-readable, "what's not committed doesn't exist"). His alternative: export the model to a **standardized JSON**, version it in git, let a local agent manipulate the JSON via provided skills, and **use MCP to validate changes pre-commit** as guardrails so the agent self-corrects; JSON feeds Build-Kit code generation (Node/Java/Kotlin).
Why it's worth reading: The clearest statement of the model-in-repo + MCP-as-guardrail pattern — the mechanism under [[dilger-event-modeling-knowledge-hub-emlang]] and the agent-harness thread.
