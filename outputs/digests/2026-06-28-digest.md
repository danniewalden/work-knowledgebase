### 1. Addy Osmani — "Loop Engineering" (addyosmani.com, 2026-06-07)
*Path:* `raw/articles/addyosmani-loop-engineering.md` — **filed 06-24, not yet ingested**

**TLDR.** The definitional primary for "loop engineering": *stop being the person who prompts the agent; design the system that prompts it for you.* Quotes Steinberger ("you should be designing loops that prompt your agents") and Boris Cherny ("I don't prompt Claude anymore… my job is to write loops"). A loop needs five primitives — **automations** (scheduled discovery/triage = the heartbeat), **worktrees** (parallel agents don't collide), **skills** (project knowledge written down once), **plugins/connectors** (the loop acts on real tools via MCP), **sub-agents** (keep the maker away from the checker) — plus a **sixth, on-disk memory** because the model forgets between runs but the repo doesn't. Maps each primitive onto both Codex and Claude Code (the capability is identical; only the names differ). Closes with three sharpening risks: verification is still yours, comprehension debt grows faster, and "cognitive surrender" is the failure mode — *build the loop but stay the engineer.*

**Why it's worth reading.** This is the cleanest articulation yet of the layer *above* harness engineering, and it directly extends your [[ralph-loop]] / [[long-running-agents]] / [[unattended-coding-agents]] thread — the "five primitives + memory" framing is a ready-made spine for a new [[loop-engineering]] concept page.

### 2. Sydney Runkle / LangChain — "The Art of Loop Engineering" (langchain.com, 2026-06-16)
*Path:* `raw/articles/langchain-the-art-of-loop-engineering.md` — **filed 06-24, not yet ingested**

**TLDR.** The vendor-side companion to Osmani: stacks four loops on top of each other — (1) **agent loop** (model calls tools until done), (2) **verification loop** (a grader, deterministic or LLM-judge, scores output against a rubric and retries on failure — maker≠checker), (3) **event-driven loop** (cron/webhook/channel triggers run the agent continuously as a background component, "always-on"), (4) **hill-climbing loop** (an analysis agent reads production *traces* and rewrites the harness config — prompt/tool/grader tweaks, or even RL fine-tuning). The key move: the outer loop's return arrow "reaches inside and updates the agent loop directly," so each cycle makes the inner loops more effective. Argues value compounds at loops 3–4, where teams have under-invested. Human-in-the-loop is a first-class touch point at every level.

**Why it's worth reading.** Gives the abstract loop-engineering idea a concrete, instrument-it-today taxonomy — and loop 4 (trace-driven self-improvement) is the missing piece that ties the harness thread to [[agent-observability-and-evals]]. Pairs with Osmani as a two-source ingest for [[loop-engineering]].

### 3. Sarang Kulkarni / Thoughtworks — "Building Reliable Agentic AI Systems" (martinfowler.com, 2026-06-16)
*Path:* `raw/articles/martinfowler-prince-building-reliable-agentic-ai-systems.md` — **filed 06-25, not yet ingested**

**TLDR.** A rare *independent, real-world* production case study: Bayer's **PRINCE** preclinical research assistant (agentic RAG + Text-to-SQL over decades of study reports), explicitly framed through **context engineering** and **harness engineering**. LangGraph multi-agent orchestration (Researcher / Reflection / Writer + a Think&Plan step) with **three distinct reflection loops** — *process* reflection (am I on the right trajectory?), *data* reflection (is the retrieved evidence sufficient?), and *draft* reflection (is the output complete?). Reliability comes from LLM fallbacks across providers, node-level retries, PostgreSQL state-persistence so a failed run resumes from the failed node, and Langfuse/RAGAS evals on both curated datasets and daily live traffic. Trust is engineered via per-sentence citations back to source chunks/page numbers and human-in-the-loop on regulatory drafts. Core lesson: "production-ready agentic AI is not about better models or prompts — it's engineering both the context the model sees and the harness within which it acts," with **context discipline** (route the *right* context to each agent, not everything) as the through-line.

**Why it's worth reading.** It's the strongest non-vendor-of-the-thesis corroboration the harness/context-engineering thread (Threads 3–4) has — a regulated enterprise system independently arriving at the KB's vocabulary — and it concretely touches [[harness-engineering]], [[context-engineering]], [[multi-agent-orchestration]], [[agent-explainability]], and [[agent-observability-and-evals]].

### 4. Adam Tornhill — "You just cannot trust your coding agent to produce maintainable code" (LinkedIn, 2026-06-22)
*Path:* `raw/notes/tornhill-cannot-trust-agent-maintainable-code-codescene-mcp.md` — **filed 06-23, not yet ingested**

**TLDR.** Tornhill's sharpest statement of the code-health-as-agent-sensor argument: told to fix a code-health issue, his agent "traded one problem for an even worse one." Asking an agent to "follow SOLID" / "write clean code," or having a second LLM review, doesn't work — LLMs are non-deterministic, have no reliable way to *assess* code health, and the messy existing code *is* the context, so agents perform worst exactly where they're needed most. His fix: deterministic **Code Health feedback via the CodeScene MCP** as the agent's external source of truth. He's coded 100% agentically for nine months and finds this "strikingly obvious beyond a toy project."

**Why it's worth reading.** It's the practitioner punchline under the peer-reviewed [[borg-tornhill-code-for-machines-not-just-humans]] finding — the "give the agent a deterministic external sensor" move is a concrete harness pattern for [[ai-readable-code]] / [[agent-legibility]] / [[harness-engineering]], and the only un-ingested item that's been waiting since 06-23.

### 5. Adam Tornhill — "An opinionated (and mainly correct) guide to naming" (Substack, 2026-06-23)
*Path:* `raw/notes/tornhill-opinionated-guide-to-naming.md` — **filed today (06-28), not yet ingested**

**TLDR.** The freshest capture. Naming as **cognitive compression that minimizes reconstruction work** for humans *and* coding agents — cites an LLM-code-understanding study (arXiv 2505.10443) finding identifier-name improvements "yielded the largest returns," plus an EMSE result that clearer names cut debugging time ~19%. Habits: name functions for the *call site* not the declaration; derive names by "Wishful Thinking" (write the ideal call first, implement second); let **domain types** free parameter names from primitive obsession; scope determines length. Anti-patterns: the `I`-prefix on interfaces, get/set procedural accessors (prefer `suspend(customer)` over `set_status(…, SUSPENDED)`), and "dumpster" names (`Utils`/`Misc`/`Helper`) that hide a real domain concept.

**Why it's worth reading.** Lowest-effort, highest-leverage entry in the [[ai-readable-code]] thread — a fresh, cited data point that naming is the single best move for agent legibility; slots straight into [[tornhill-ai-readable-code-series]]. Caveat: explicitly an opinion piece, studies cited second-hand.
