## Read next

1. **Agent Skills for Software Development — the "factory pipeline" (John Wilger, GitHub `jwilger/agent-skills`)** · `raw/articles/jwilger-agent-skills-event-modeling-factory-pipeline.md` · *filed, not yet ingested*
   **TLDR:** A portable Agent-Skills repo (v4.1, ~145 commits) that encodes a full disciplined SDLC for any coding agent — `event-modeling` is the "understand" skill that produces swimlanes + GWT scenarios, which then feed an autonomous pipeline: event model → GWT → vertical slices → autonomous TDD → mob code-review → mutation testing → CI. It also ships an `ensemble-team` skill that stands up a tiered AI "expert team" with consensus planning (Robert's Rules), ping-pong TDD pairing, and retrospectives.
   **Why it's worth reading:** This is the *human-authored Event Model as the spec that drives a team of coding agents* — the exact opposite direction from Dymitruk's "agents as users/processors inside a model" and Qlerify's "AI assists modeling". It's the most concrete EM→agent-factory artifact in the KB and directly extends [[event-modeled-agent-design]] and the Triplet/software-factory threads.

2. **"My Wife Asked Me to Build a Registration Form for a Flea Market" (Martin Dilger, LinkedIn, 2026-07-01)** · `raw/notes/dilger-flea-market-model-code-deploy-30min.md` · *filed, not yet ingested*
   **TLDR:** A narrative demo: Dilger models a real flea-market registration app *with* his non-technical wife on the Eventmodelers platform — just by drawing the screens, she follows along and effectively co-authors the spec (registration → paid-by-hand tracking → spreadsheet export), and he takes it model→code→deploy fast. The point is that the visual event model is a shared language a layperson can drive, and the platform collapses the model-to-running-app distance.
   **Why it's worth reading:** A ground-level illustration of the "requirements are part of the architecture / model-first with stakeholders in the room" claim from the Triplet, and of [[vibe-modeling]] in practice — the accessibility case for EM as the stakeholder interface to an agent build.

3. **"Remember the microservices hype 12 years ago? — the AI '(s)loop' as the new Holy Grail" (Vlad Khononov, LinkedIn, 2026-06-30)** · `raw/notes/khononov-microservices-hype-to-ai-sloop.md` · *filed, not yet ingested*
   **TLDR:** A short, pointed contrarian jab from a coupling/modularity author: the "AI loop / thousands of deploys a day" enthusiasm is the same pattern as the microservices hype — a crowd chasing something most of them can't define, which ended in distributed monoliths and monorepos-to-cope. He's implicitly asking what the hangover-cure will be this time.
   **Why it's worth reading:** It is the **only skeptic/counterweight primary** on the entire loop-engineering thread, which is otherwise dominated by advocates (Osmani, swyx, LangChain, AHE). Worth reading precisely to stress-test the loop/software-factory narrative you've been accumulating.

4. **"Are you using Draw.io for Event Modeling?" — model-in-code + MCP guardrails (Martin Dilger, LinkedIn, 2026-06-30)** · `raw/notes/dilger-drawio-event-modeling-model-in-code.md` · *filed, not yet ingested*
   **TLDR:** Dilger agrees clients want "the model in the code" and that draw.io XML in the repo is a decent free option — but flags its drawbacks (XML unreadable without a viewer, non-technicians can't contribute, and crucially *AI has no framework/rules so it makes mistakes*). His pitch: model → export standardized JSON → version in git → let a local agent manipulate the JSON via skills, **but gate every change through an MCP validator** so the agent gets guardrails and self-corrects before commit.
   **Why it's worth reading:** A crisp statement of the "give the agent a deterministic validator, not just a prompt" principle applied to the event model itself — ties [[fraktalio-event-modeler-connect-ai-agents-mcp]], [[esdm-event-sourced-domain-modeling]], and Tornhill's external-sensor argument to EM tooling.

5. **"Extending Event Modeling: an optional 'Query' (WHEN) on the read side" (Martin Dilger, LinkedIn, 2026-06-29)** · `raw/notes/dilger-extending-event-modeling-query-when.md` · *filed, not yet ingested*
   **TLDR:** Notable as the *first time* Dilger deviates from the Event Modeling "Standard" — he's a self-described purist (his book and the Eventmodelers platform stick to Dymitruk's original elements). After repeated independent requests at the Munich EM Conference (and prior discussion with Dymitruk himself), he proposes adding a way to express complex **queries** inside GWT scenarios on the read side, and is explicitly seeking community feedback rather than asserting it.
   **Why it's worth reading:** A live signal of the EM notation itself evolving — relevant to [[given-when-then]] and how agent-consumable specs represent read-side behavior; also a data point on where the method's standardization is under pressure.
