`raw/notes/khononov-modularity-claude-code-plugin.md` — **filed, not yet ingested** (freshest unprocessed input).
**TLDR:** Khononov shipped his Balanced Coupling model as a runnable Claude Code plugin with two skills: `/modularity:review` audits an existing codebase for coupling imbalances across integration-strength/distance/volatility and emits a Markdown+HTML review with coupling.dev links; `/modularity:high-level-design` does the inverse — designs a modular architecture from requirements, writes per-module contracts and test specs, then self-reviews and iterates until clean. **2. Coupling — research note (boundary edge-weights)** *(deep-research run for you, 2026-06-22)*
[[coupling-research-note]] — **new wiki source page** (raw verbatim at `raw/notes/coupling-research-note.md`).
**TLDR:** Surveys the coupling literature to answer one product question — what a dependency-edge weight should *mean* on a user-needs/capability map — and lands on Khononov's Balanced Coupling as the direct fit. Recommends a **two-dial** editor UX: **Integration Strength** (intrusive→functional→model→contract) as primary and **Volatility** (judged via DDD subdomain, not commit history) as secondary, while treating **Distance** as a property of the *partition*, not the edge. Classical 1974 taxonomy = vocabulary mismatch; Team Topologies = partition-side constraints; change-coupling = wrong shape (telemetry, not editor judgment).
**Why it's worth reading:** This is the first time the "good boundaries make code tractable" strand turns into a concrete product-design decision for *your* tool — and it flags the open product calls (per-map vs global weights, numeric mapping) you'd need to settle. Note its honesty: the recommendation is synthesis, and three adjacent claims were adversarially killed (Khononov's Distance over-spec, Team Topologies group-size cutoffs, ISH-as-cognitive-load).

**3. Coupling Taxonomy (the landscape)** *(new concept, from the research note)*
[[coupling-taxonomy]] — **new wiki page.**
**TLDR:** A side-by-side map of how the field grades coupling — Stevens/Myers/Constantine 1974 (six ordinal levels, intra-program), Khononov 2024 (strength × distance × volatility, the recommended fit), Team Topologies 2019 (interaction modes, no edge scale), and change-coupling (VCS-mined co-change) — plus a note on why graph-partitioning metrics (Martin instability, Newman/Louvain) answer "how to partition," not "what the weights mean."
**Why it's worth reading:** The compact orientation page for the boundary-weighting work; tells you at a glance which framework fits a capability-graph edge and which are category errors.

**4. Roden — Event Sourcing meets MCP: the whole story for LLMs** *(Golo Roden, the native web / EventSourcingDB; heise, Apr 2026)*
[[roden-event-sourcing-meets-mcp-whole-story-for-llms]] — **new wiki page.**
**TLDR:** Event sourcing solves the *data* problem (complete, business-language history) and MCP solves the *access* problem; CRUD-over-MCP hands an LLM "only the last chapter," an event store gives it "the whole story." Events are argued to be the natural language for LLMs (business-named, chronological, self-contained), and EventSourcingDB ships a free MCP server exposing them — though the principle is pitched as product-neutral.
**Why it's worth reading:** The cleanest articulation yet of the event-sourcing × MCP × context-engineering bridge, and a new ES-vendor voice distinct from Akka/Critter/Axon — directly on your EM×agents focus and the MCP seam.

**5. AxonIQ — AI Agent Explainability: Why Your Infrastructure Needs to Remember** *(Reeves & Buijze, AxonIQ; Apr 2026)*
[[axoniq-ai-agent-explainability-why-infrastructure-needs-to-remember]] — **new wiki page.**
**TLDR:** Agent explainability is an infrastructure problem, not a model problem — only an event *store* (full causal context, replayable) can answer *why* a decision was made, where an event *stream* (Kafka) only moves *what*. Frames this against EU AI Act / SR 11-7 / GDPR Art. 22, and pairs the explainability payoff with Roden's context payoff: same immutable log, two wins.
**Why it's worth reading:** Supplies the regulatory/audit framing the ES-as-agent-memory thread was missing, and the sharp event-store-vs-stream distinction refines your agentic-EDA picture. Caveat baked in: it's a promotional Axon post and the "resists hallucinations" line is an unquantified anecdote.

**6. Borg, Tornhill et al. — Code for Machines, Not Just Humans** *(FORGE 2026, peer-reviewed; arXiv 2601.02200)*
[[borg-tornhill-code-for-machines-not-just-humans]] — **new wiki page.**
**TLDR:** First peer-reviewed grounding for the code-health × agentic thread: across 5,000 Python files with a unit-test pass oracle, LLMs break Healthy code (CodeHealth ≥9) **15–30% less often**, and CodeHealth predicts refactoring correctness better than perplexity or SLOC. Practical takeaway: route AI work by code health, reserve human oversight for unhealthy code.
**Why it's worth reading:** Upgrades the "bad code degrades the agent" claim from vendor LinkedIn posts to a citable, oracle-backed result — and is distinct from the separate 35–45% token-spend marketing figure. Caveat: competitive-programming Python, CodeScene-affiliated authors.
