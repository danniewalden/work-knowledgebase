**2. Dilger — "How I use Local-LLMs to build software systems" (two-part series), LinkedIn ~07-02** — *filed, not yet ingested* — `raw/notes/dilger-local-llm-distributed-agent-setup-event-modeling.md`

- **TLDR:** A concrete implementation report of Dilger's always-on build factory. Hardware: 3 on-prem Asus GX10 boxes running local models (Gemma4 ~60 tok/s, Qwen3.6:27B ~30 tok/s) via Ollama, harnessed by Claude Code / OpenCode (+ a Hermes agent); 6–10 agents in ralph-loops 24/7, mostly building, 1–2 modeling. The synchronization trick is dead simple: when a slice hits "Planned," exactly one agent **claims and locks it** → "In Progress," so others move on — "no collisions, no merge conflicts, no coupling hell." Comments and voice-to-text spawn Modeling Tasks; agents self-provision per-stack Build-Kits/Modeling-Kits; moving a slice "Done"→"Planned" makes an agent reconcile code back to spec. He calls EM + Event Sourcing + Slice-Based the "triplet of flexible architectures."
- **Why it's worth reading:** This is the first time the abstract "Event Modeling Agent Harness" gets pinned to real hardware, real models, and a real concurrency mechanism (the claim-lock). It directly enriches `[[dilger-event-modeling-agent-harness]]` and `[[dilger-model-is-a-living-spec-always-on-agent]]` with implementation evidence.

**3. Dilger — "Extending Event Modeling: an optional 'Query' (WHEN)", LinkedIn ~06-29** — *filed, not yet ingested (backlog)* — `raw/notes/dilger-extending-event-modeling-query-when.md`

- **TLDR:** Dilger's **first-ever deviation from the Event Modeling "standard."** Prompted by repeated independent feedback at the Munich conference (and a prior discussion with Dymitruk), he adds an optional "Query" WHEN to the read side of Given-When-Then: instead of `GIVEN event / THEN data available`, you can now write `GIVEN event / WHEN we query by X / THEN expect Y` — letting scenarios express complex queries. He stresses he's seeking broad feedback, not imposing it.
- **Why it's worth reading:** A rare change to the EM notation itself, straight from a core practitioner, and it directly touches `[[given-when-then]]` — the acceptance-gate seam your agent-harness thread relies on. Durable, worth capturing before it becomes ambient.

**4. Dilger — "Are you using Draw.io for Event Modeling?" (model-in-code), LinkedIn ~06-30** — *filed, not yet ingested (backlog)* — `raw/notes/dilger-drawio-event-modeling-model-in-code.md`

- **TLDR:** On keeping "the model in the code." Dilger agrees the model belongs in the repo, and acknowledges clients use draw.io XML + AI to manipulate it — but flags the drawbacks (XML isn't human-readable, non-technicians can't contribute, AI has "no framework, no rules"). His alternative: export to a standardized JSON, version it in git, let a local agent manipulate the JSON via skills, and use **MCP to validate changes before commit** as guardrails so the agent self-corrects. Supports codegen via Build-Kits (Node/Java/Kotlin).
- **Why it's worth reading:** The clearest statement yet of the model-in-repo + MCP-as-guardrail pattern — the model-in-code and agent-harness threads meeting in a concrete workflow.

**5. Dilger — "My Wife Asked Me to Build a Registration Form for a Flea Market", LinkedIn ~07-01** — *filed, not yet ingested (backlog)* — `raw/notes/dilger-flea-market-model-code-deploy-30min.md`

- **TLDR:** A short real-world anecdote: a non-technical stakeholder (his wife) modeled a flea-market registration by drawing screens, and it went model→code→deploy in under 30 minutes — because the tooling, architecture and event-store decisions were made *before* they started.
