### 1. Nick Tune — "Enforced application architecture for agents and humans" *(nick-tune.me, 2026-08-13)*

`raw/articles/nick-tune-enforced-application-architecture-agents-humans.md` — **filed, not yet ingested**

**TLDR.** Tune's frustration is that agents ignore architectural guidance no matter where you write it — "AI does dumb stuff like that all the time even with a million lines of markdown screaming at it not to do that." So he stops writing guidance and fails the build instead. His tool **Rivière** enforces three tiers over an NX/TypeScript monorepo: *package classification* (a `packages/{subdomain}/domain-model` may contain only `/domain` and may only import `published-language` — anything else is a hard build failure), *layer rules* (folder→folder import permissions), and *role rules as a last resort* (code annotated `@riviere-role` as aggregate / value-object / domain-event / domain-port / domain-service / domain-error, so `/data-access` can import an aggregate but never a domain-service). Role *shape* constraints are explicitly anti-drift: a value-object must be a class with a private constructor and a branded private member, so "AI cannot implement an aggregate inside value-object because an aggregate-repository must return an aggregate." His honest cost accounting: package/domain/layer rules are cheap and "I find it hard to justify not adding those"; full role annotation is "still playing around with that. Come back in 6 months."

**Why it's worth reading.** It's the [[fitness-functions]] page's missing worked primary (that page is 308 words and has no real example), and his use-cases package — `/features/{feature}` with `importRules: { allow: {} }`, no sharing between feature folders — is **[[vertical-slice-architecture]] enforced by the build**, independently corroborating Dudycz's "everything outside the slice is external." He also keeps ADR-002 and the executable config deliberately aligned, which is a concrete answer to [[dilger-is-code-still-the-source-of-truth]].

### 2. Martin Dilger — the trust pair: "The lights-off software factory is a dead end" (08-16) + "Trust needs to be engineered" (08-15)

`raw/notes/dilger-lights-off-software-factory-dead-end.md`, `raw/notes/dilger-trust-needs-to-be-engineered.md` — **filed, not yet ingested**

**TLDR.** Two halves of one argument, and the Event-Modeling camp's direct reply to [[addyosmani-software-factories-light-and-dark]]. The problem statement: full code review doesn't scale with agent output ("you just moved the bottleneck") but no review fails at the first production incident — "production burning and no one there to navigate the code base (as no one has ever seen it)." Every team he knows that went lights-off circled back. His answer is **layers of trust**: Event Model as spec → GWT scenarios → executable specifications ("call it Test-First Development if you will, as we define the tests long before any code") → a **static gate whose four rules are the interesting part** (were tests adjusted? are there tests outside the spec? were files changed outside the Slice-Under-Development — *immediate fail*; were dependencies changed?) → a 2–3 minute *structural* human review, not a functional one. Failure means throwing the slice away, recording a "why", and moving it back to planned. He names the whole thing the **Triple-Architecture**: SDD via Event Modeling + structure via Slices + implementation via Event Sourcing. The companion post supplies the evidence: a **non-engineer** ("probably never wrote a line of code before") driving boards via AI + MCP and shipping slices — "Not a benchmark, not a demo." The thesis line: "**AI can write good code. The thing is, you just can´t trust it to do so reliably. The real issue is trust.**" And the payoff: "That's how you work around the review bottleneck. Not by doing more reviews, but by making most of them obsolete."

**Why it's worth reading.** This is the sharpest practitioner statement yet of the KB's central EM×agents claim — that modelling upfront is a *trust-engineering* mechanism, not documentation — and it pairs exactly with Tune's enforce-don't-document position from a completely different tradition. Also the strongest [[vibe-modeling]] data point since the flea-market post. One naming job falls out of it: "Triple-Architecture" vs "the Triplet" ([[dilger-triplet-flexible-agent-enabled-architecture]]) need reconciling on one concept page.

### 3. MacManus × Fred Schott — "React for Agents: Astro Creator Brings Hooks to his Meta-Harness, Flue" *(Latent.Space, 2026-08-15)*

`raw/articles/macmanus-schott-react-for-agents-flue-meta-harness.md` — **filed, not yet ingested**

**TLDR.** Schott (Astro creator, now Cloudflare) ships Flue 2, where an agent is a JavaScript function that "**re-renders on every turn**", with 16 built-in hooks — `useSkill()`, `useTool()`, `useSubagent()` — that let agents "attach different resources and capabilities dynamically to enhance themselves at runtime." He explains the pivot: file-based routing was the naive port from web frameworks, but "their whole company is one agent. They don't care about routing", so composability replaced routing and React replaced Next.js as the model. The quotable line for the KB: "**Our early bet was that the harness is actually not a feature, but it's fundamental to what you think an agent is. There is no agent without a harness.**" He maps the layer too: Flue (on **Pi**, a minimal open-source harness — Pi:Flue :: Vite:Astro) and Vercel's **eve** treat the harness as built-in, versus OG frameworks (Vercel AI SDK, Cloudflare Agents SDK, Mastra) bolting one on. Bret Taylor's "we're sort of in the jQuery era of agents, not the react era" is the framing.

**Why it's worth reading.** It resolves the standing Omnigent/meta-harness flag and gives the KB a vendor-neutral primary for harness-as-constitutive. The hooks API is the five primitives of [[addyosmani-loop-engineering]] reappearing as a *composition* API — worth reading against your loop-engineering page before it gets rewritten.

### 5. The arXiv harness pair — Evo-Bench (2608.09096) + SBCO (2608.10157), both 2026-08-10

`raw/papers/evo-bench-can-language-models-improve-agent-harness.md`, `raw/papers/sbco-verifier-grounded-harness-optimization.md` — **filed, not yet ingested**

**TLDR.** *Evo-Bench* is the benchmark counterpart to [[ahe-agentic-harness-engineering]]: "the first benchmark designed to evaluate models' intrinsic harness-evolving capabilities", built specifically to isolate harness improvement from base-model strength. Top models gain up to **16.6 absolute points, "closely approaching state-of-the-art human-engineered baselines"**; autonomous evolution beats hand-built harnesses on General and excels on Search, but **struggles on Office tasks "that demand highly specific processing workflows"**; it exposes temporal anomalies like early saturation; and synthesised harnesses transfer as "highly transferable reasoning structures" across policy models. *SBCO* states the precondition the practitioner literature never does: self-*referential* self-improvement only works where "the competence required to perform the task coincides… with the competence required for self-modification, **which is the case for coding tasks**" — so the whole Ralph-loop/factory literature is quietly leaning on coding being a special case. Its alternative is self-*supervised*: learn a decomposed bank of **verifiers** plus a harness policy by approximate block coordinate ascent from graded feedback, no human labels, matching a self-modifying baseline at **4–5.5× less compute**.

**Why it's worth reading.** Together they give the loop/harness thread its first academic spine, and the Evo-Bench Office finding is the useful one for you: the self-improving loop fails precisely where the domain has idiosyncratic process — which is the Event Modeling wheelhouse, i.e. an argument *for* modelling rather than against it. (Related signal: the arXiv API shows ~25 "agent harness" papers in the last two weeks alone; the academic tier is now outrunning the blog tier.)

### 6. Martin Dilger — "How to Model UI-Only Interactions: A Filtering Example" *(eventmodelers.ai, 2026-07-31)*

`raw/articles/dilger-ui-only-interactions-filtering.md` — **filed, not yet ingested; out-of-window backfill awaiting your accept/reject**

**TLDR.** Answers a recurring modelling question — "how would you model filtering a table of books by genre?" — with: most of the time, **you don't**. No Command, no Event. You define one Read Model (`Books[]`) and use **Multi-Screen Views** to show Page 1 unfiltered and Page 2 with the filter applied, both backed by the same read model, then describe behaviour with a Query-based GWT scenario ("Given two `Book registered` events… When you query by title… Then the read model returns just that one match") that is "stated purely in terms of the data" with nothing about UI plumbing. The UI mockup itself is accessible to a connected agent building from the model. Conclusion: "you can show in one slice how the system should behave without inventing state changes that don't exist in the domain."

**Why it's worth reading.** It's the anti-pattern correction for the most common modelling mistake — inventing events for UI state — and it shows the mockup-plus-GWT combination being consumed by an agent, which is [[event-modeled-agent-design]] at the level of one concrete slice. Six minutes.
