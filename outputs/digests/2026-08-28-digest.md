## Read next

### 1. Rico Fritzsche — "Why the Entity Model Is an Illusion: What Remains When You Model What Happens"
`raw/articles/fritzsche-why-the-entity-model-is-an-illusion.md` — *filed, not yet ingested*

**TLDR.** Fritzsche's sharpest statement yet of the entity-vs-event position: we don't need entities defined in advance, because "the existence of a unique identifier does not automatically constitute an entity." His worked example is vehicle rental, where registering a car is *not* `CreateVehicle` ("that merely describes a database operation… the car rental company doesn't actually 'create' a vehicle") but a sequence — `VehicleAcquired → VehicleReceived → VehicleInfleeted → VehicleReleasedForRental`. **The Vehicle is a projection, not an entity**; an ID (artificial or a VIN) is only a *reference*. Capabilities like `AcquireVehicle` and `ReceiveVehicle` are "autonomous, self-contained, and coherent… they share only the Application State — an Event Store and the event definitions. However, they know nothing about each other." The two-cost argument against load-mutate-save is quotable: it "destroys the information about what happened" and "turns every concurrent request into a conflict we have to defend against" — with audit/history/status/changelog tables read as workarounds for information the last-write row already threw away.

**Why it's worth reading.** This is the top-priority focus thread — **business capabilities** — getting its cleanest primary yet, and it hands you a ready-made argument for capability autonomy that doesn't route through DDD aggregates. His "every form is a projection… it's simply a different matter from the perspective of purchasing versus the repair shop" also rhymes directly with EM swimlanes.

### 2. The Miller-vs-Dilger DSL-vs-code controversy pair (read them back to back)
`raw/articles/miller-jasperfx-critterstack-ai-event-modeling-strategy.md` + `raw/notes/dilger-markdown-is-a-suggestion-dressed-as-a-spec.md` — *both filed, not yet ingested*

**TLDR.** Miller (2026-08-21) lays out JasperFx/CritterStack's whole AI strategy and, at the end, commits to **landing Event Modeling into the core of the Critter Stack** — a fluent `JasperFx.Events` API to declare event types and read models, a Bobcat UI that *visualizes* those slices, `dotnet watch` for interactive doodling, BDD specs wired straight into the visualization ("rather than have people waste time writing intermediate models for policies, constraints, or validation rules in a diagram, go straight to… actionable specs"), CLI export of slice definitions for agents, and codegen of a slice shell. Then the philosophical knife: "I'm not enthusiastic about any of the intermediate DSL approaches I'm seeing for modeling event driven architectures using YAML, XML, or custom built textual DSLs… we're better off just adding the visualization capabilities on top of the code." Dilger (2026-08-25) argues the exact inverse: "It's ridiculous we've chosen Markdown as the 'language' for LLMs… The Markdown we use is a suggestion dressed up as a spec. We have a formal language — it's called Code… Spec-Driven Development requires suitable language. Event Modeling is the one that works for me."

**Why it's worth reading.** Two credible practitioners agree Event Modeling is the right frame for AI-assisted development and land on **opposite substrates** — code-as-source-of-truth with the model as a view (Miller) vs. the model as the formal spec language (Dilger) — and both invoke "code is the real formal language" to get there. This is the sharpest live tension on the EM×agents seam, and it bears directly on whether your own `.chspec.yml` work sits with Dilger or against Miller.

### 3. Oskar Dudycz — "Vertical slices, their ownership and external dependencies"
`raw/articles/dudycz-vertical-slices-ownership-and-external-dependencies.md` — *filed, not yet ingested — **18 days waiting***

**TLDR.** Dudycz answers the five VSA questions that keep recurring (table per slice? seven areas = seven contexts? how does "verify order" read what "register order" wrote? where does cross-module fetching live?) by naming the assumption doing the damage: "a slice ought to be self-contained, so needing something from elsewhere means the cut was wrong." He separates **slice / module / context** as three different things, argues that calling every application area a bounded context "sets the bar for separation as high as it can go" and thereby makes every legitimate connection look like a violation — and then gives the *positive* answer he says he skipped in his earlier slicing posts: "minimise isn't zero, so what does the non-zero look like once you type it out?"

**Why it's worth reading.** The longest, most concrete piece in the queue (25 KB) on **vertical slice architecture**, and it fills the exact gap Miller's post assumes away — what a slice is allowed to know. It's also the substrate thread's only in-queue primary while Topic-3 discovery sits at 13 empty sweeps.

### 4. Simon Willison — "Breaking Claude Code Opus 5 Auto Mode"
`raw/articles/willison-breaking-claude-code-auto-mode.md` — *filed today, not yet ingested*

**TLDR.** A short link post, but an empirical counter-datum to vendor safety claims. Anthropic recently made Claude Code's auto mode the default "and have made bold claims about its effectiveness"; Johann Rehberger found an attack that **works 80% of the time** — trick Claude Code into downloading and uncompressing a zip, then run code that imports `base64` without noticing that this also imports and executes a `struct.py` extracted from the archive. The sharpest finding is that **the guardrail became part of the failure**: "Claude tried to terminate the malware process once it noticed the compromise, but Auto Mode denied the cleanup command… The classifier allowed the creation of the malware process, but then it blocked the command intended to stop it!" Conclusion: the only safe way to run agents under adversarial risk is a sandbox — container/VM, restricted egress, monitoring, no home dirs/SSH keys/cloud credentials in the agent runtime.

**Why it's worth reading.** It's the first **hard empirical bound** this KB holds on how much autonomy an always-on loop can be granted, and the takeaway is architectural, not incidental: *a classifier is not a substitute for an isolation boundary.* Sits directly next to Osmani's back-pressure and Willison's own DRI/sandbox line.

### 5. Addy Osmani — the loop-engineering trio (Aug 2026)
`raw/articles/addyosmani-practical-loop-engineering.md`, `addyosmani-agentic-code-quality.md`, `addyosmani-human-judgment-relocates.md` — *all three filed, not yet ingested*

**TLDR.** In *Practical Loop Engineering* Osmani describes running "anywhere between five and ten agents working at the same time in parallel," splitting work by whether he can state the stopping conditions ("tasks I'm very happy to delegate fully to agents, as long as I have a very clear idea of the stopping conditions and the constraints") versus tasks he code-reviews closely. He then marks the shift from **hand-rolled bash loops** (the Ralph loop era, deliberately on low-stakes personal projects) to loops as **first-class product primitives** — Claude Code's `goal` (drive one bounded task to a measurable finish line) and scheduled `loop` (rerun on a timer) — with the anatomy being goal → act → evaluate against a strong check → feed back.

**Why it's worth reading.** The best-organized practitioner account in the queue of loop engineering *after* the primitives shipped, and the "strong check" is exactly the seam where a slice's given/when/then would plug in. Cheapest high-value ingest in the queue — three related pieces, one page each, one session.
