### 1. Simon Willison — "More than just code review" (simonwillison.net, 2026-08-22)
`raw/articles/willison-more-than-just-code-review.md` — *filed today, not yet ingested; short-form note, captured in full*

**TLDR.** Four sentences, and the whole argument is in them: the key skill for productive agent use is "being able to confidently instruct them on how to make changes and then confidently **verify** that those changes have been applied in the correct way." Reviewing every line is *one* instrument for that, not the instrument — "eyeballing every line of code has never been the most effective way to validate a chance [sic] to a piece of software." It narrows his Aug-19 *Conceptual integrity and counting lines of code* argument (cognitive capacity, not code production, is the new ceiling) onto the verification half of the loop specifically.

**Why it's worth reading.** It's the shortest thing in the backlog and it hands the Event-Modeling seam its opening: if line-by-line review isn't the best verification instrument, a slice's given/when/then is a direct candidate for the "other way" — and Willison, who has no stake in Event Modeling, is the one saying the door is open.

### 2. Rico Fritzsche — "Thinking in Events" (ricofritzsche.me, 2026-07-03)
`raw/articles/fritzsche-thinking-in-events.md` — *filed 08-07, un-ingested 16 days*

**TLDR.** Fritzsche separates two things the KB's own pages routinely bundle: **Event Modeling is a modeling discipline; Event Sourcing is an implementation choice**, and conflating them "turns a useful way of thinking into another technical prescription." The argument runs through a booking domain: projects fail not from complexity but from *losing the language that explains it* — a conversation about reservations, hosts and cancellations degrading into records, flags and status columns. His sharpest operational point is about naming: `ReservationUpdated` is weak because it "preserves the mutation and loses the reason," collapsing a guest changing dates, a host cancelling, support correcting an error and a platform no-show into one indistinguishable write; `ReservationCanceled` / `CheckInDateChanged` / `ReservationMarkedAsNoShow` keep the rule, authority, timing and downstream consequence visible. He credits Dymitruk's method directly (imagine the system exists, ask which facts would have been captured as time moves forward, then add what users see).

**Why it's worth reading.** Fritzsche is the KB's primary capabilities voice, and this is the piece that lets the value of Event Modeling be argued **without** committing to the event store — which is exactly the argument you need when pitching EM as an agent-design substrate to a team that will never adopt Event Sourcing.

### 3. Oskar Dudycz — "Vertical slices, their ownership and external dependencies" (Event-Driven.io, 2026-08-10)
`raw/articles/dudycz-vertical-slices-ownership-and-external-dependencies.md` — *filed 08-15, un-ingested 14 days — the oldest August capture still waiting*

**TLDR.** Dudycz collapses five recurring vertical-slice questions ("a table per slice?", "are seven areas seven bounded contexts?", "how can *verify order* read what *register order* wrote if they mustn't know about each other?") into one: **what does a slice do when it needs something from outside?** He names the assumption doing the damage — that a slice ought to be self-contained, so needing anything external means the cut was wrong — and rejects it: "minimise isn't zero." The corrective is vocabulary discipline separating **slice** (one piece of functionality cut through the whole application; "more a function than an entity" — *verify a transport order*), **module**, and **bounded context**; calling every area a context sets the separation bar as high as it goes and leaves legitimate connections with no legal answer.

**Why it's worth reading.** Vertical slice architecture is thin in the wiki relative to its weight in your focus, and this is the piece that gives the *positive* rule for cross-slice dependencies — load-bearing for whether a slice can be an agent's unit of work at all. It has now been recommended for three digests running.

### 4. Martin Dilger — "How to Model UI-Only Interactions: A Filtering Example" (eventmodelers.ai, 2026-07-31)
`raw/articles/dilger-ui-only-interactions-filtering.md` — *backfilled 08-17, not yet ingested*

**TLDR.** The method-level answer to a question Dilger says he's answered dozens of times verbally and never written down: **UI-only interaction typically involves no Command and no Event.** Filtering a book list is modelled as two pages over the *same* `Books[]` read model (unfiltered / filtered) using Multi-Screen Views — "no round trip to a Command, no new Event" — and its behaviour is still pinned down by a Given/When/Then stated purely in data terms (given two `Book registered` events, when query by title "Harry Potter", then the read model returns that one match), so the scenario is independent of UI plumbing. Generalised rule: "Filtering, sorting, expanding a row, switching a tab — these are all views on data you already have. Model them as Views, not as Commands looking for an Event to justify them."

**Why it's worth reading.** `wiki/overview.md` has "deeper Event Modeling mechanics not yet pulled" as a standing open item, and this closes a concrete anti-pattern: inventing state changes that don't exist in the domain. It also matters for the agent seam — the mockup plus GWT is explicitly what a connected agent builds from, so the slice stays a complete agent work order even when nothing is appended.

### 5. Rachel Laycock — "Citizens Build, Agents Execute, Experts Govern" (martinfowler.com, 2026-08-19)
`raw/articles/laycock-citizens-build-agents-execute-experts-govern.md` — *filed 08-20, not yet ingested; pairs with `laycock-the-conductor-developer.md`*

**TLDR.** Thoughtworks' CTO on the gap that opened over six months — not a technology gap but a gap in what different people think software engineering *is*. Her diagnosis is self-inflicted: "we've spent so many years banging on about how to write good software that everyone has assumed writing software is the same as software engineering." The weekend app is real software; what changes when the business depends on it is the *questions* (is customer data protected, what happens when a dependency fails, can someone understand this in two years, will it survive an audit, how will we know something is wrong before customers do) — and those questions don't appear in a demo unless an experienced engineer is in the room. Reporting from FOSE, she notes the interesting part of the overnight-agent pipeline wasn't the pipeline but what the humans did: "deciding what good looked like, making trade-offs and judging whether what came back was actually what they wanted." Hence the slogan, and the line under it: **"Organisations don't run on code. They run on trust."** What's scarce now is engineering judgement, not code.

**Why it's worth reading.** Read back-to-back with her Conductor Developer piece (already in `raw/`), this is the executive-altitude statement of the attention/judgement bottleneck that Miracle derives mechanically from Amdahl's law and Dilger derives from the review-bottleneck argument — three independent routes to the same claim, which is the strongest synthesis sitting unwritten in the backlog.
