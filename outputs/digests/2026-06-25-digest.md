## Read next

**1. Loop Engineering — Addy Osmani (addyosmani.com, 2026-06-07)** · `raw/articles/addyosmani-loop-engineering.md` · *filed, not yet ingested*

TLDR: The definitional primary for "loop engineering" — the move from prompting an agent to *designing the system that prompts it for you* ("I write loops, not prompts," per Steinberger/Cherny). Osmani locates loop engineering "one floor above the harness" and decomposes a loop into five product primitives now shipping in both Codex and Claude Code — automations (the scheduled heartbeat), worktrees (parallel isolation), skills (codified intent), plugins/connectors (MCP into your real tools), sub-agents (maker≠checker) — plus a sixth: on-disk memory, because the model forgets between runs but the repo doesn't. He's pointedly skeptical: verification stays on you, comprehension debt and "cognitive surrender" get *worse* as the loop gets smoother, and two people running the identical loop get opposite outcomes depending on whether they use it to go faster on work they understand or to avoid understanding it.

Why it's worth reading: This is the cleanest naming yet of the layer above your harness-engineering thread, and it maps the loop primitives directly onto the exact tooling (skills, sub-agents, scheduled tasks, worktrees) this KB's agentic-coding focus tracks — a ready-made concept page [[loop-engineering]] sitting on the [[ralph-loop]]/[[long-running-agents]]/[[harness-engineering]] seam.

**2. The Art of Loop Engineering — Sydney Runkle (LangChain blog, 2026-06-16)** · `raw/articles/langchain-the-art-of-loop-engineering.md` · *filed, not yet ingested*

TLDR: The same idea rendered as a concrete 4-loop stack (after swyx's "loopcraft"): Loop 1 = the agent (model + tools); Loop 2 = a verification loop with a deterministic-or-LLM grader that retries on rubric failure; Loop 3 = an event-driven loop (cron/webhook) that makes the agent always-on inside your ecosystem; Loop 4 = a "hill-climbing" loop where a trace-analysis agent reads production traces and *rewrites the harness config itself* — automating improvement, not just work. The key move: Loop 4's return arrow doesn't loop to the top, it reaches inside and edits the inner loops. Each level has an explicit human-in-the-loop touchpoint (and a LangChain primitive: RubricMiddleware, LangSmith cron/Engine, Fleet channels).

Why it's worth reading: Pairs with Osmani as the engineering-mechanics half of the same thread — the hill-climbing loop (traces → harness rewrite) is the precise feedback-loop analogue to Böckeler's sensors and your [[feedforward-and-feedback-controls]] / [[fitness-functions]] material, and "embed agents in your ecosystem that continuously improve" is the unattended-coding payoff stated as a loop.

**3. Building Reliable Agentic AI Systems (PRINCE) — Sarang Kulkarni / Thoughtworks (martinfowler.com, 2026-06-16)** · `raw/articles/martinfowler-prince-building-reliable-agentic-ai-systems.md` · *filed, not yet ingested*

TLDR: A rare *production* agentic-AI case study with real engineering depth — Bayer's preclinical research assistant (agentic RAG + Text-to-SQL over decades of study reports), explicitly retold "through the lens of context engineering and harness engineering." The design discipline is context routing: each stage gets only its own context (planning → Think&Plan, retrieval → Researcher, evidence → Reflection, synthesis → Writer) rather than one bloated prompt — bigger context windows did *not* remove the need to be selective. Three distinct reflection loops (process / data / draft), LangGraph orchestration with per-node state persistence in Postgres for resume-from-failure, LLM fallbacks across providers, Langfuse + RAGAS evals on both datasets and daily live traffic, and citation-based explainability with human-in-the-loop on regulatory drafts.

Why it's worth reading: It's independent, real-world corroboration for the harness/context-engineering thread (Threads 3/6) from a non-vendor venue (Fowler's site, though authored by a Thoughtworks colleague, *not* Böckeler — judge ingest priority accordingly), and it concretely touches [[agent-explainability]], [[agent-observability-and-evals]] and [[multi-agent-orchestration]] with a shippable architecture rather than a manifesto.
