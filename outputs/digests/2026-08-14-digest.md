## Read next

### 1. Birgitta Böckeler — "TDD inside the agent loop — theater or actual value?"
*martinfowler.com, "Exploring Gen AI" series, 2026-08-10 · `raw/articles/bockeler-tdd-inside-the-agent-loop.md` · **filed, not yet ingested***

**TLDR.** Böckeler ran an exploratory eval — 5 batches of small/medium/large greenfield business-logic tasks, Sonnet 4.6 generating, Opus 4.8 blind-ranking the solutions — to test whether instructing an agent to follow TDD *inside its own loop* actually helps. It doesn't: no discernable quality difference, and the **non-TDD runs were ranked slightly higher on design and test quality more often than not**, with no meaningful mutation-score gap, at **3–8.5× the token cost**. The mechanism she hypothesises from the traces is the interesting part: non-TDD and test-first runs did **full up-front design** (architecture, data types, edge cases, contracts) before writing anything, whereas TDD instructions actively suppress that step — design emerged from locally-minimal decisions, was rarely revisited, and locked into whatever shape the first test happened to take. "Behaviour the agent didn't think to write a test for didn't get implemented at all." She then audits TDD's goals one by one and finds most were *human* benefits: red-green proves nothing when the same agent writes the test and confirms the failure; Beck's "managing fear" doesn't transfer; agents overshoot minimal implementations because they already hold the whole spec. Her conclusion — stop specifying *how* the model should work, monitor **outcomes** instead (mutation testing as the regression sensor, static analysis + periodic AI modularity review as refactoring triggers, Ördög's "Approved Scenarios" for confidence). She has stopped telling coding agents to do TDD.

**Why it's worth reading.** It's the sharpest empirical challenge yet to the KB's own GWT-first through-line — and the distinction matters: her finding argues against **agent-invented micro-TDD**, *not* against human/model-authored acceptance specs, which is exactly the line Dilger and jwilger are on. Read it to know where the KB's `[[given-when-then]]`-as-acceptance-gate claim is safe and where it isn't.

### 2. Rico Fritzsche — "Thinking in Events"
*ricofritzsche.me, 2026-07-03 · `raw/articles/fritzsche-thinking-in-events.md` · **filed 08-07, never ingested — and not referenced anywhere in `wiki/`, including `log.md`***

**TLDR.** Fritzsche's cleanest statement of a distinction the KB keeps circling: **Event Modeling is a modeling discipline, Event Sourcing is an implementation choice, and conflating them "turns a useful way of thinking into another technical prescription."** Worked through a hotel-booking domain: the failure mode isn't complexity, it's *losing the language that explains the complexity* — a conversation about reservations, guests, availability and cancellations degrading into records, flags and status columns. `ReservationUpdated` is weak because it preserves the mutation and loses the reason; `ReservationCanceled` / `CheckInDateChanged` / `ReservationMarkedAsNoShow` keep the business distinction (different rules, authority, timing, consequences) visible. He ties this to DDD's Ubiquitous Language ("*rigorous* is the important word — software does not handle ambiguity well"), argues an Event Model is "less forgiving" than a table because every fact must justify its place in the timeline, and insists the value of the method is that **the conversation changes before technical design hardens** — after which tables, documents, messages or an event store are all still open choices.

**Why it's worth reading.** This is the one piece in the KB that cleanly separates the method from the store, which is the load-bearing distinction under Thread 6 — and it's been sitting in `raw/` unnoticed for a week. It also complements `[[fritzsche-choosing-storage-is-choosing-what-your-system-forgets]]` from the modeling side rather than the storage side.

### 3. Oskar Dudycz — "Fixing bugs in Event Sourcing is hard, for real?"
*Architecture Weekly / event-driven.io, 2026-07-27 · `raw/articles/dudycz-fixing-bugs-in-event-sourcing.md` · **filed 08-10, still not ingested***

**TLDR.** A Tuesday-morning support ticket ("the price on this reservation looks wrong") used to argue the opposite of the usual complaint. In a mutable model, the row doesn't record how the number was produced — no breakdown, no rate version, `updated_at` pointing at an unrelated later edit — so your data-fix migration **overwrites the evidence you'd need to check whether the fix worked**, and attempt 3 ends up computed from attempt 2's output. In ES the original events are immutable, so every correction is computed from the booking. Four practical primitives: (1) put `metadata.buildSha` on events so you can query the exact rows a broken binary produced (900 genuinely wrong vs 340 merely touched) plus correlation/causation IDs; (2) fix forward with an appended corrective event (`ReservationPriceCorrected` — the accountant's correcting entry), never edit events in place; (3) make correction a **first-class command** (`CorrectReservationPrice`, with permissions and a mandatory reason) so the bulk fix runs the same path a front-desk operator would — nobody `UPDATE`s prod at 23:00; (4) skip streams where a price-affecting event follows the bad one, because a blind bulk recalc silently undoes a human's deliberate goodwill correction.

**Why it's worth reading.** It's the operational counterweight to the substrate thread's mostly-conceptual DCB/CCC arguments — concrete enough to lift into practice, and it opens a concept the KB doesn't yet have (corrective/compensating events + build-SHA event metadata).
