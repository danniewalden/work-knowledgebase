## Read next

### 1. Drew Breunig — "Harnesses are Situated Agents" (dbreunig.com, 2026-08-14)
`raw/articles/breunig-harnesses-are-situated-agents.md` — *filed today, not yet ingested*

**TLDR.** Breunig's one-line definition: a harness **is** an agent that has been *situated*. Harrison Chase's four agent elements (system prompt, planning tool, file system, subagents) describe only "the core loop the developer controls with the keyboard"; the harness manages the eight layers fanning outward from it — **Session** (trajectory as a durable, branchable log you can rewind, fork and replay) → **Environment** (sandbox/terminal/worktree/container) → **Repo** (git, `AGENTS.md`, guides, hooks) → **Memory** → **Skills** (reusable workflows and domain knowledge) → **Team** (shared rooms, shared traces, issue trackers) → **Organization** (policy, audit, legal, procurement) → **Model**. The ordering rule is the payload: *"as we move outward, each layer is used by more people and changed less often."* He backs it with a dated Aug-2026 harness census (Databricks Omnigent as a meta-harness, DeepSeek Harness modular down to loops and scheduling, Block's Buzz, YC's QM with org-shaped scoping, Cloudflare Flue which "hides the loop from users", Meta's Muse Code whose model was co-trained *with* its harness, plus OpenClaw/NanoClaw/Hermes/Conductor/Prime Agent) and closes on a strategy claim: harness switching costs are the SaaS-style network effect the labs have been hunting for.

**Why it's worth reading.** It's the strongest definitional primary for `[[harness-engineering]]` since Böckeler's guides/sensors framing — and the layer ordering is really a **coupling/volatility argument** (outer = more shared, less volatile), which is Khononov's balanced coupling in a different costume. Layers 4–5 (Memory, Skills) are precisely where an Event Model would sit as durable domain knowledge, which makes this the cleanest available answer to "where does the model live in an agent system?"

### 2. Drew Breunig — "Fable & The End of the Free Lunch" (dbreunig.com, 2026-08-23)
`raw/articles/breunig-fable-and-the-end-of-the-free-lunch.md` — *filed today, not yet ingested; companion to #1*

**TLDR.** The economic case for harness engineering, argued by analogy to Herb Sutter's "free lunch". While each new model landed at the same price or cheaper and "papered over most of your problems", it "felt silly to waste *too* much time improving your coding harness or context strategies." Once frontier cost stopped being amortised away — Fable being incredible but expensive, while Opus 5, 5.6, K3 and GLM were good enough for most code — *"we started to think about what work went where."* Concretely: GLM 5.2 at roughly 1/9th Fable's cost is "more than sufficient" for rote coding, *"**especially** when provided with great context"*; his own workflow is to chat with Fable to interrogate and shape a design, then hand a **brief** to GLM. He rebuts the falling-price counterargument twice over — cheaper inference lifts the K3s and Qwens equally, and better harnesses make it easier to give weaker models sufficient context — and notes Fable's access controls, dynamic degradation and data-retention requirements pushed orgs (and countries) into thinking about where their traces and tokens go.

**Why it's worth reading.** This is a first-class argument for the wiki's central seam, arriving from someone with no stake in Event Modeling: a well-specified slice plus its given/when/then **is** the "sufficient context" that lets a cheap model execute a brief. That turns specification quality into an *economic* lever, not just a correctness one, and makes model routing a harness design decision. Read immediately after #1 — they're a pair, and together they're a two-hour ingest that meaningfully upgrades two concept pages.

### 3. Nick Tune — "Enforced application architecture for agents and humans" (nick-tune.me, 2026-08-13)
`raw/articles/nick-tune-enforced-application-architecture-agents-humans.md` — *filed 08-17, un-ingested 7 days*

**TLDR.** Tune's complaint is the one everybody has: AI-generated code ignores architectural guidance written in skill files, ADRs and markdown scattered round the repo. His answer is to stop *relying* on prose and make the architecture a build failure. The mechanics: **classify packages by type** (a `domain-model` package is not a CLI app and shouldn't obey the same rules), **prefer broad layer-level rules** (folder A cannot import from folder B), use **fine-grained role-based rules only as a last resort** (data-access may import an aggregate but not a domain service), and **enforce domain boundaries** — a `packages/{subdomain}/domain-model` package may contain only a `/domain` root, may only hold code annotated with a declared role (`aggregate`, `value-object`, `domain-event`, `domain-port`, `domain-service`, `domain-error`), and may not import from another subdomain's domain model. Anything else is a hard build fail. Implemented as a DSL over NX monorepos in TypeScript.

**Why it's worth reading.** It's the deterministic counterpart to every "write it in AGENTS.md and hope" harness pattern in the KB, and it lands on your top-priority axis: **subdomain boundaries as compile-time facts** is capability boundaries made enforceable. If a slice is going to be an agent's unit of work, this is the machinery that stops the agent from quietly dissolving the boundary the model drew.

### 4. Oskar Dudycz — "Vertical slices, their ownership and external dependencies" (Event-Driven.io, 2026-08-10)
`raw/articles/dudycz-vertical-slices-ownership-and-external-dependencies.md` — *filed 08-15, un-ingested 14 days — the oldest August capture still waiting*

**TLDR.** Dudycz collapses five recurring vertical-slice questions ("a table per slice?", "are seven areas seven bounded contexts?", "how can *verify order* read what *register order* wrote if they mustn't know about each other?") into one: **what does a slice do when it needs something from outside?** He names the damaging assumption — that a slice ought to be self-contained, so needing anything external means the cut was wrong — and rejects it: *"minimise isn't zero."* The corrective is vocabulary discipline separating **slice** (one piece of functionality cut through the whole application; "more a function than an entity" — *verify a transport order*), **module**, and **bounded context**; calling every area a bounded context sets the separation bar as high as it goes and leaves legitimate connections with no legal answer.

**Why it's worth reading.** Vertical slice architecture is thin in the wiki relative to its weight in your focus, and this gives the *positive* rule for cross-slice dependencies — load-bearing for whether a slice can be an agent's unit of work at all. Fourth digest running that it's been recommended; it pairs naturally with #3, which is the enforcement mechanism for exactly these rules.

### 5. Rico Fritzsche — "Thinking in Events" (ricofritzsche.me, 2026-07-03)
`raw/articles/fritzsche-thinking-in-events.md` — *filed 08-07, un-ingested 17 days — the oldest item in the backlog*

**TLDR.** Fritzsche separates two things the KB's own pages routinely bundle: **Event Modeling is a modeling discipline; Event Sourcing is an implementation choice**, and conflating them "turns a useful way of thinking into another technical prescription." Argued through a booking domain: projects fail not from complexity but from *losing the language that explains it* — a conversation about reservations, hosts and cancellations degrading into records, flags and status columns. The sharpest operational point is naming: `ReservationUpdated` is weak because it "preserves the mutation and loses the reason", collapsing a guest changing dates, a host cancelling, support fixing an error and a platform no-show into one indistinguishable write; `ReservationCanceled` / `CheckInDateChanged` / `ReservationMarkedAsNoShow` keep the rule, the authority, the timing and the downstream consequence visible. He credits Dymitruk's method directly.

**Why it's worth reading.** Fritzsche is the KB's primary capabilities voice, and this is the piece that lets the value of Event Modeling be argued **without** committing to an event store — exactly the argument you need to pitch EM as an agent-design substrate to a team that will never adopt Event Sourcing.
