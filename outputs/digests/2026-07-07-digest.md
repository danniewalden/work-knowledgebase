## Read next

**1. Dilger — "How does DCB affect Event Modeling?"**  *(new wiki page; tightest focus)*
`[[dilger-how-does-dcb-affect-event-modeling]]`
- **TLDR:** After modeling several systems with Dynamic Consistency Boundaries, Dilger concludes DCB doesn't complicate Event Modeling — it *simplifies* it. You model one swimlane per bounded context and swimlanes go back to meaning *integration between systems/teams* rather than stream design. You never model a separate "Decision Model": the GIVEN clause of a GWT scenario already specifies exactly the events a command handler needs. DCB makes decisions granular (a per-handler Criteria query in Axon), and the Axon Build Kit generates that Criteria code *and* the test cases straight from the model — "AI is really good at that." Tags are indices, not domain concepts, so don't model them.
- **Why worth reading:** This is the payoff on a question the KB has tracked since the Munich conference, and it directly wires your three focus areas together — EM × agents (model→GWT→generated code) and the DCB substrate. The "GWT GIVEN *is* the decision context" insight is new to the wiki.

**3. Willison — "Vibe engineering"**  *(filed 07-06, NOT ingested and NOT in the log — orphaned capture)*
`raw/articles/willison-vibe-engineering.md`
- **TLDR:** Willison's Oct-2025 coinage for the *responsible* end of the LLM-coding spectrum (opposite of vibe coding), later renamed "agentic engineering" per his Feb-2026 update. Core argument: LLMs actively *reward* top-tier engineering practices — automated testing (test-first especially), planning in advance, comprehensive docs, good Git habits, CI/automation, a code-review culture, and "a very weird form of management." Working productively with agents is genuinely *difficult* and raises the bar for the human's contribution.
- **Why worth reading:** It's the definitional origin of the vibe-coding↔agentic-engineering distinction the `agentic-coding` page leans on, and it's currently sitting in `raw/` uningested and unlogged — worth reading so you can decide whether it earns its own page or folds into the existing Willison pages.

**4. Willison — "Designing agentic loops"**  *(new wiki page; loop-engineering)*
`[[willison-designing-agentic-loops]]`
- **TLDR:** The earliest named statement of loop design in the KB (Sept 2025, nine months before the Osmani/swyx "loop engineering" crystallization). Agents are brute-force solvers; the skill is designing the tools + loop. Four practical moves: YOLO mode + sandboxing (the agent-safety angle the 2026 sources under-weight — GitHub Codespaces, Anthropic Safe YOLO), prefer shell commands over MCP + document tools in AGENTS.md, issue tightly-scoped credentials with budget caps, and know when to loop (clear success criteria + tedious trial-and-error, enabled by a passing test suite).
- **Why worth reading:** Gives the loop-engineering thread a 2025 origin and the security/mechanics dimension the enthusiast 2026 primaries skip — useful counterweight and grounding for your harness/loop substrate.

**5. Willison — "Agentic Engineering Patterns" (guide)**  *(new wiki page; agentic-coding)*
`[[willison-agentic-engineering-patterns]]`
- **TLDR:** Willison's continuously-updated guide to getting good results from coding agents. Crisp definition — "agents run tools in a loop to achieve a goal," and for coding agents one tool executes code, which is what makes iterate-to-working-software possible. Key stances: the human job shifts (deciding *what*, specifying at the right level, verifying) rather than shrinks; "agents don't learn, harnesses do" (a direct harness-engineering statement); and vibe coding ≠ agentic engineering.
- **Why worth reading:** The hands-on practitioner complement to Fowler/Böckeler (conceptual) on the agentic-coding thread, and it explicitly echoes Dilger's "requirements are the 80%" line — a nice cross-thread bridge.
