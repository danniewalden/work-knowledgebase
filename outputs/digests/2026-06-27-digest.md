**1. Loop Engineering — Addy Osmani (addyosmani.com, 06-07) + "The Art of Loop Engineering" — Sydney Runkle (LangChain, 06-16)** · `raw/articles/addyosmani-loop-engineering.md`, `raw/articles/langchain-the-art-of-loop-engineering.md` · *filed 06-24, not yet ingested*

TLDR: A matched primary pair naming the layer **one floor above the harness**. Osmani's definitional piece: loop engineering is "replacing yourself as the person who prompts the agent — you design the system that does it instead" (Steinberger/Cherny: "I write loops, not prompts"). A loop is five product primitives now shipping in both Codex and Claude Code — automations (scheduled discovery/triage), worktrees (parallel isolation), skills (codified project knowledge), plugins/connectors (MCP into real tools), sub-agents (maker≠checker) — plus a sixth, on-disk memory, "because the agent forgets, the repo doesn't." He is pointedly skeptical: verification stays on you, and comprehension debt / "cognitive surrender" get *worse* as the loop smooths out. Runkle renders the same idea as a concrete 4-loop stack: agent → verification (grader/rubric, retries) → event-driven (cron/webhook, "always-on") → hill-climbing (a trace-analysis agent that **rewrites the harness config itself**), where Loop 4's return arrow reaches inside and edits the inner loops.

Why it's worth reading: It's the cleanest framing yet of the loop layer sitting directly on your `harness-engineering` / `ralph-loop` / `long-running-agents` / `unattended-coding-agents` focus, and its primitives map exactly onto the tooling this KB tracks (skills, sub-agents, scheduled tasks, worktrees). **2. Building Reliable Agentic AI Systems (PRINCE) — Sarang Kulkarni / Thoughtworks (martinfowler.com, 06-16)** · `raw/articles/martinfowler-prince-building-reliable-agentic-ai-systems.md` · *filed 06-25, not yet ingested*

TLDR: A rare *production* agentic-AI case study with real engineering depth — Bayer's preclinical research assistant (agentic RAG + Text-to-SQL over decades of study reports), explicitly retold "through the lens of context engineering and harness engineering" (terms applied in hindsight). **3. "You just cannot trust your coding agent to produce maintainable code" — Adam Tornhill (LinkedIn, 06-22)** · `raw/notes/tornhill-cannot-trust-agent-maintainable-code-codescene-mcp.md` · *filed 06-23, not yet ingested*

TLDR: Tornhill (9 months coding 100% agentically) hits the wall again: told an agent to fix a specific code-health issue and got "a software design disaster where one problem was traded for an even worse one." His argument: asking an agent to "follow SOLID" / "write clean code" or having a second LLM review it doesn't work, because (a) LLMs are non-deterministic, (b) an LLM has no reliable way to assess code health, and (c) the messy existing code *is* the context, so agents perform worst exactly where they're needed most. His fix: deterministic Code Health feedback via the **CodeScene MCP** as the agent's external source of truth, rather than asking it to judge its own output.

Why it's worth reading: It's the practitioner sharp-end of your `ai-readable-code` / code-health × agentic thread — the LinkedIn complement to the peer-reviewed Borg/Tornhill FORGE paper already ingested, and a concrete "deterministic sensor over the agent" pattern for `harness-engineering` and `agent-legibility`. Ingesting it updates `adam-tornhill`, `ai-readable-code`, `harness-engineering`.

**4. Announcing Strictland — Oskar Dudycz (Event-Driven.io, 06-15)** · `raw/articles/dudycz-strictland-contract-testing-message-compatibility.md` · *filed 06-18, not yet ingested (the oldest un-ingested keeper)*

TLDR: Dudycz releases **Strictland**, a JVM OSS contract-testing library for message/event schema compatibility. Instead of brokers/registries (Pact, Spring Cloud Contracts, Schema Registry), it serializes a message in an ordinary unit test and commits the JSON as a snapshot file beside the code, so any format change shows up in a normal diff. `thenContractIsUnchanged()` catches accidental drift; `thenBackwardCompatible()` / `thenForwardCompatible()` confirm an older and newer version can still read each other's data — using your app's own ObjectMapper so the snapshot is the exact bytes you ship. Pre-1.0; .NET and TS ports planned.

Why it's worth reading: It's a concrete, tooling-level answer to your `event-versioning-and-upcasting` substrate question — "how do you stop an event schema change from stranding events already in the store" — and a lightweight alternative to the upcasting debate running through the Dilger/Pellegrini/Atomic-Object material. Smallest of the four, but it's been waiting the longest and is squarely on the substrate focus.
