### 1. Thinking in Events
**Rico Fritzsche**, ricofritzsche.me, 2026-07-03 · `raw/articles/fritzsche-thinking-in-events.md` · *filed, not yet ingested — the oldest item in the real queue (captured 08-07)*

**TLDR.** Fritzsche's argument is a clean separation the KB has been circling: **Event Modeling describes behaviour; Event Sourcing decides where authority for state lives** — "Event Modeling names the facts; Event Sourcing makes the fact history authoritative." He builds it on a booking domain: `ReservationUpdated` is a weak event because it "preserves the mutation and loses the reason" — it collapses a guest changing dates, a host cancelling, support correcting a mistake, and a no-show into one shape, when each carries different rules, authority, timing and consequence. Naming them separately (`ReservationCanceled`, `CheckInDateChanged`, `ReservationMarkedAsNoShow`) makes the next questions concrete: who may do it, when is it valid, what becomes available again, is a refund due. He then makes the decisive move, quoting Dymitruk — *"Events happen — whether we store them or not is our choice"* — so a team can model in events while still writing current state to relational tables; the test for Event Sourcing is only whether the event history is the **authoritative** application state. And the reverse holds: an event store full of `ReservationUpdated` "may technically use Event Sourcing while still preserving a CRUD-shaped understanding" — "storing vague events only preserves the vagueness permanently."

**Why it's worth reading.** It is the most quotable statement of the boundary your substrate focus keeps needing — Event Modeling is usable without buying event sourcing — and it hands `[[event-modeling]]` and `[[event-sourcing]]` a shared, source-backed dividing line instead of the current implicit coupling between them.

### 2. Vertical slices, their ownership and external dependencies
**Oskar Dudycz**, event-driven.io, 2026-08-10 · `raw/articles/dudycz-vertical-slices-ownership-and-external-dependencies.md` · *filed, not yet ingested — queued 4 days*

**TLDR.** Dudycz starts by de-conflating three words: a **vertical slice** is one piece of functionality cut through the whole app and is "more a function than an entity" (*"Verify a transport order"*); a **module** is a logical grouping of slices, grouped by *what changes together*; a **bounded context** is "a linguistic barrier" — a set of functionality the business uses one vocabulary for. Frontend and backend are **two deployment targets, not two contexts**, and "seven features of one application are almost always slices, or at most modules, inside a single context — that's good news, because it means they were never obliged to be autonomous." He then answers the question `[[vertical-slice-architecture]]` leaves open — what does a slice do when it needs something it doesn't own? — with **everything outside the slice is external** as one category (the next folder, the parent module, another module, a third-party API, the database), and the slice **declares a narrow function type in its own vocabulary** (`CheckContractor = (id) => Promise<'Active'|'Unknown'|'Suspended'>`) rather than importing a wide provider interface, composed by hand-rolled partial application. Underneath it all is Greg Young's Task-Based UI point: if every operation is "update the order" you have one feature and nothing to divide; naming `VerifyOrder`/`ConfirmOrder`/`RejectOrder` is what gives you folders to slice along — "the name is the value, and the underlying implementation can be a single `UPDATE`."

**Why it's worth reading.** `[[vertical-slice-architecture]]` is one of the thinner pages on your substrate spine (86 lines) and this is the best answer it lacks; it also pairs directly with the un-ingested Nick Tune piece — Dudycz says *no sharing between feature folders*, Tune makes the build fail when you try.

### 3. Fixing bugs in Event Sourcing is hard, for real?
**Oskar Dudycz**, Architecture Weekly, 2026-07-27 · `raw/articles/dudycz-fixing-bugs-in-event-sourcing.md` · *filed, not yet ingested (captured 08-10)*

**TLDR.** A worked incident, not an argument from principle. A hotel tourist tax rises from 4.50 to 7.00 on 1 April; the new lookup resolves the rate **once per reservation from the check-out date**, so stays crossing the boundary get charged the April rate for March nights. In the **state-based** system the row can't answer "what should this have been": no breakdown, no rate-plan version, and `updated_at` reflects the breakfast someone added, not the booking. The recompute migration therefore matches 1,240 rows of which only ~900 are actually broken, and — because `recalculate_total` reads *today's* rate plan, revised on 15 March — it turns a wrong total into a differently wrong total while destroying the evidence needed to try again. **Event-sourced, the move is to fix forward:** don't edit history ("you should not change the past… even including bugs, is a valid scenario"), append a `ReservationPriceCorrected` event with previous total, corrected total and reason — "the accountant's move: we don't rub out a ledger line, we post a correcting entry next to it" — then rebuild the read models. If the *correction* is also wrong, the original 14 March events are still there, so attempt three is computed from the booking rather than from attempt two. Bonus effect: the correction is itself a visible fact, so the next person to open the stream (and the front desk, if surfaced) sees that a bug happened, when, and why.

**Why it's worth reading.** It's the operational case for the substrate you're betting on, in the terms sceptics actually raise ("bugs are harder to fix"), and the fix-forward pattern is the missing counterpart to the correction/compensation seam in `[[event-sourcing]]` — plus the "correction as a feature the front desk can see" angle feeds `[[agent-legibility]]`.

### 4. Loop Engineering — Or Why You Should Never Argue With an Agent
**Martin Dilger**, eventmodelers.ai, 2026-06-10 · `raw/articles/dilger-loop-engineering-never-argue-with-agent.md` · *filed, not yet ingested — the window's only new capture; composed in full in yesterday's digest*

**TLDR (short form).** Long agent conversations poison the context — "confusion is what produces hallucination… the predictable result of a polluted context window" — so each iteration gets defined goals and rules, and a broken rule means discarding everything **except the recorded learnings** and retrying from a cleared context. Event Modeling *is* loop engineering applied, because the hard part of a loop is the task list and every slice is a task with a status (Planned = claimable by an agent, then Done / Blocked / timed-out). Closing warning: don't engineer the loop — "more state, more memory, more decision-making between iterations" rebuilds the noise the loop existed to remove.

**Why it's worth reading.** Still the highest-value unread item for the EM × agents focus: the authored primary `[[loop-engineering]]` has been proxying through Osmani, LangChain and swyx for six sweeps. If you only clear one file this week, clear this one.
