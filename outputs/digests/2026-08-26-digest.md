### 1. Jeremy D. Miller — "The JasperFx / CritterStack AI and Event Modeling Strategy" (*The Shade Tree Developer*, 2026-08-21)

`raw/articles/miller-jasperfx-critterstack-ai-event-modeling-strategy.md` — **filed, not yet ingested**

**TLDR.** Miller lays out how JasperFx is betting the Critter Stack on AI-assisted development, and Event Modeling is now core to that bet: a fluent model API in `JasperFx.Events` for declaring event types and read models, a **Bobcat** UI that visualizes EM slices, `dotnet watch` integration so you can "interactively doodle with slice definitions and see the model change", EM concepts pushed *directly into Wolverine and the Marten/Polecat/Fisher event stores*, codegen that builds "the shell of a 'slice' from the model", and — the part aimed straight at your work — "more command line options to **export the event slice definitions for AI agent usage**" plus AI Skills that teach an agent to use those specs. He also argues VSA was **accidentally prescient token economics**: layered architectures "force AI agents to burn more tokens traversing the code". Then the sting: he is "not enthusiastic about any of the intermediate DSL approaches I'm seeing for modeling event driven architectures using YAML, XML, or custom built textual DSLs" and would rather add "visualization capabilities on top of the code".

**Why read it.** This is the strongest Event-Modeling-×-agents primary in weeks *and* a dated, named challenge to the `.chspec.yml` premise from someone shipping a competing implementation of the same idea. You need his argument in your own words before you can answer it.

### 3. Martin Dilger — "Slice-based architecture is not really about slices" (LinkedIn, 2026-08-25)

`raw/notes/dilger-element-slice-chapter-story-context-ladder.md` — **filed, not yet ingested**

**TLDR.** Introduces a **new method vocabulary ladder: Element → Slice → Chapter → Story → Context.** A slice is only "the smallest building block you can model"; group slices and you get a *chapter* (a consistent part of a business process or customer journey); order chapters and you get a *story* (the whole flow end to end); many stories form a *context* (a complete system). Diagnosis: "Most teams get stuck right there. They model slice after slice and never climb up to see the story."

**Why read it.** It's a genuine Event Modeling method extension with no equivalent anywhere in `wiki/concepts/` — and it's a ready-made zoom hierarchy for anything that has to navigate a large model (a chspec file, a diagram renderer, an agent reading slices). Short read, high structural value.

### 4. Adam Tornhill — "Controlling the Uncertainty Machine: Do You Still Need to Read AI Code?" (*Code for Humans and Machines*, 2026-08-20)

`raw/articles/tornhill-controlling-the-uncertainty-machine.md` — **filed, not yet ingested**

**TLDR.** "**Human inspection is driven by uncertainty**" — task uncertainty sets both the autonomy granted and the review depth (a bug fix: inspect only the evidence; a first iteration on a novel feature: spot-inspect structure, never all the code). The mechanism is **tests as the human/agent abstraction boundary**: have the agent generate e2e tests first, review and iterate on *those* heavily ("AI-generated application code is rarely optimal… but usually decent. The test code? Not so much"), then let it write whatever makes them pass. Two further rules: **turn review findings into future guards** (don't fix it yourself — have the agent capture the transformation as a forward-looking SKILL), and **enforce what you don't inspect** deterministically (linters, CodeHealth MCP, custom architectural checks). Restates the CodeScene finding that "a coding agent is even more picky about code quality than we humans."

**Why read it.** It completes a three-way convergence with Willison's "More than just code review" (08-23) and Osmani's "Agentic Code Quality" (08-08): all three independently conclude that reading every line is the wrong unit and all three replace it with a verification artefact. For this wiki the punchline is one sentence — **Tornhill's reviewed-e2e-test boundary is a slice's given/when/then**, arrived at without any EM vocabulary.

### 5. Dan McAteer — "The Evolution of the Agent Harness" (*Latent.Space*, 2026-08-22)

`raw/articles/mcateer-evolution-of-the-agent-harness.md` — **filed, not yet ingested**

**TLDR.** The best-argued *historical* account of harness engineering in the KB. Two curves — what the harness asks of the model vs. what the model can deliver — and the gap between them *is* agent effectiveness, traced through four dated stages: ReAct as "the harness on paper" (Oct-2022), AutoGPT/BabyAGI "premature autonomy" (Spring-2023, with the compounding math: 95% per step over 20 steps ≈ 36% success), Cursor/Copilot's "retreat to human in the loop", and Claude Code where "the curves cross" (Feb-2025). Then **Harness 2.0, the co-training era**, with hard numbers: **Harness-Bench — same model, same 106 tasks, 52.4 → 76.2 across harnesses, a 23.8-point spread with zero model change** ("half the agent is the harness"); Anthropic deleting 80% of Claude Code's system prompt. That yields the loop **train → absorb → shed → repeat**, and the metric "the measure of the pace of agent harness evolution is **how much of the harness you get to delete**". Finally **Harness 3.0, the attention era**: absorption doesn't end the harness, it *inverts* it — permissions, identity, trust and legibility can never be absorbed, so "the harness becomes the model's interface to our human attention", an **attention-interface** he predicts will ship as ubiquitously as AGENTS.md.

**Why read it.** It gives you a defensible number for the "the harness matters as much as the model" claim, and its endpoint — a formal surface governing when an agent may spend human attention — is the same destination as Osmani's "human judgment relocates", reached from the opposite direction. Useful framing for where a model artefact sits once the harness dissolves.

### 6. Richard MacManus interviewing Matt Pocock — "The /wayfinder Skill: Navigating the 'Fog of War' of Planning" (*Latent.Space*, 2026-08-20)

`raw/articles/macmanus-pocock-wayfinder-skill-fog-of-war.md` — **filed, not yet ingested**

**TLDR.** Pocock describes an orchestrator-layer planning skill for AFK/overnight agents, built on a deliberate **map / ticket / session** vocabulary and a "fog of war" metaphor for decisions you can't make up front (ticket kinds: grilling, prototype, research, task). The design method is the interesting part: "if you just call everything a ticket… it's going to be really confused and you're going to get strange behavior", so he uses "**leading words**", maintains an AI-coding dictionary shared across every one of his skills, and concludes: "**I realized that I needed a ubiquitous language between me and the agent**… and agents are really good at showing you the opportunities for different wording — **really good at domain modeling, actually.**"

**Why read it.** A DDD/ubiquitous-language conclusion reached independently from the agent-skills side, by someone with no EM exposure. It's the strongest outside corroboration yet that glossary/ubiquitous-language work is harness infrastructure rather than documentation — which is the whole premise behind curating a glossary alongside a model.
