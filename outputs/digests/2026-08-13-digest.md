## Read next

**1. "Fixing bugs in Event Sourcing is hard, for real?" — Oskar Dudycz (Architecture Weekly / event-driven.io, 2026-07-27)**
`raw/articles/dudycz-fixing-bugs-in-event-sourcing.md` — *filed 08-10, not yet ingested (the only un-ingested source in the KB).*
TLDR: A hotel-pricing bug (a tourist-tax rate lookup that mis-charges stays crossing a rate boundary) is the setup for the real argument: in a mutable/state-based model a data-fix migration **overwrites the very evidence** you'd need to check whether the fix worked, so each migration ends up repairing the last one. Event sourcing avoids this because the original events are immutable — every correction is computed from the booking, not from the prior fix. Dudycz gives four concrete primitives: (1) stamp each event with `metadata.buildSha` (+ correlation/causation IDs) so you can query the exact rows a broken binary produced; (2) fix-forward with an appended corrective event (`ReservationPriceCorrected` — the accountant's correcting-entry move), never editing events in place; (3) make correction a first-class command (`CorrectReservationPrice`, with permissions + a mandatory reason) so a bulk fix runs through the same path as a front-desk operator; (4) skip streams the customer already fixed, so a blind bulk recalc doesn't silently undo a human's deliberate goodwill correction.
Why it's worth reading: it's the substrate thread's sharpest practical piece on *operating* an event-sourced system, and the build-SHA-as-event-metadata idea is a clean bridge between the ES store and agent/CI provenance — directly relevant to your ES/CQRS focus. It's also the thing to green-light so it stops sitting in `raw/`.
